# Changelog

All notable changes to Arc CMS will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/), and this project adheres to [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- **The deploy sets the cleanup policy for old function images.** Before every deploy with functions, `npm run deploy` (guided, with options, `deploy:dev`, `deploy:prod`, CI) runs `firebase functions:artifacts:setpolicy` for the `gcf-artifacts` repository in the functions region, so old container images are deleted and the Firebase CLI never stops at its own "How many days do you want to keep container images" question, which showed only as a bare `>` inside the deploy, or fails a deploy off a terminal. On a project's first deploy the repository does not exist yet: the deploy sets the policy as soon as the deploy creates it, before the CLI checks. It is remembered in `.arc-deploy-state.json` and never stops a deploy. New key `artifactCleanupDays` (`arc:configure --artifact-cleanup-days=<days>|none`, default 1; `none` keeps every image). See docs/operations/deploy.html#old-function-images.
- **The sign-in page says it is working.** After the last digit of a PIN or code, or Continue, the line under the step says "Checking…" at once, "Still checking…" after 4 seconds and "No answer yet. Check your connection." after 12, the boxes and buttons still until the answer. The busy button keeps the only spinner; the line has words alone. `<arc-wait-line>` and `waitStage()` do the same on an app's own screens (`[spinner]="false"` under a button that spins itself). Each step also wakes the functions it calls as it opens. See docs/app/sign-in.html#waiting.
- **`src/custom/sign-in-page.ts`**, a new starter file: `opened` and `signingUp` hooks, each with `warm(names)` to start the app's own functions while the person types. The app kit exports `isWarmUp` and `WARM` for them. See docs/app/sign-in.html#page-hooks.
- **`ARC_KEEP_WARM`** in `functions/.env.<project>` keeps instances of chosen functions running on that project. See docs/app/functions.html#keep-warm.
- **Repeat from a number in templates.** `data-arc-repeat="rating"` repeats an element's children as many times as a number says, for star ratings, progress dots and meters: one child for every slot (told apart by `{{ @state }}`: full, half or empty), two for full and half, three for full, half and empty. `data-max` caps the number and sets the slots, and each copy can use `{{ @index }}`, `{{ @number }}`, `{{ @percent }}` and more. Works in detail, list and card templates and the home page's card blocks, published and in the app; at most 100 copies, and a value that is not a number counts as 0. A number field's Template Reference snippet mentions it. See docs/features/templates.html.
- **Crop images in the media manager.** Select an image and press **Crop**: pick Free, Original, 1:1, 4:3, 3:4, 3:2 or 16:9, then move and resize the frame. An upload's crop is saved as a new image at all four sizes and the original is left alone (new callable `readMediaImage` hands the browser the upload's bytes, so no bucket CORS setup is needed); an Unsplash photo is cropped through its URL (`rect`) and still used from Unsplash. A caller opening the picker can pass `cropRatio` to start the frame on its slot's shape. `arc-image-cropper` (`src/shared/components/image-cropper/`) and `src/shared/utils/image-crop.ts` are there for an app's own pages. See docs/features/media.html.
- **The country beside a mobile number.** On the sign-in page the "Phone number or email" field shows the number's country (flag and calling code) as soon as it holds a number, and a list to change it when the site takes several countries; the profile's number box and the SMS test send have it too. A pasted or autofilled `+44 ...` number moves its code to the country, a number from a country the site does not take is refused at once naming the ones it takes, and the server gets the number with its code. The chip starts on the country this device used last, else the default. See docs/features/sign-in.html.
- **Settings, SMS picks countries, not codes.** **Countries** lists the countries people can sign in from, with flags and a search by name, ISO id or code; **Default country** shows when there are several. `Settings/sms` stores `defaultCountry` and `allowedCountries` beside the calling codes the server reads, and `Settings/users` gets `phoneCountry` and `phoneCountries` for the sign-in page. A site saved before reads each saved code as its main country until it is saved again. See docs/features/sms.html.
- `arc-phone-country`, `arc-country-picker`, the country table (`src/shared/data/countries.ts`, flags in `public/flags` from flag-icons, MIT) and `src/shared/utils/phone-country.ts`, for an app's own number boxes. See docs/app/custom-space.html.
- **The app owns its website.** Home page, header, footer, sign-in panel, content templates, static pages, strings, site styles, favicon and error pages live in `src/custom/site/`, laid over Arc CMS's defaults in `public/_site/`. See docs/website/overview.html.
- **The home page is published as a static page** in every language, from `src/custom/site/home.html` (or `home.{lang}.html`), with SEO tags and live parts run by `/assets/js/arc-site.js`. **Republish website** on the Content types page publishes everything again.
- **`npm run arc:own-site`** moves a site an app edited in `public/` into `src/custom/site/`.
- In `npm run dev`, the editor says **Live site differs** when your site files are not the live ones yet.
- **Cards from content types without public pages.** A type with **Generate public pages** off shows in the home page's card block, through its **Card template**, with no links. Services, a hero or testimonials are edited in the admin without each item getting a page. See docs/website/editable-sections.html.
- **Card blocks in the header and footer.** `<arc-content-partials>` in `src/custom/site/header.html` or `footer.html` shows its cards on every page: published content, list, static and home pages have them in their HTML, and the pages the app draws show the same cards. When what such a block shows changes, the whole site is published again, in a release of its own, once however many entries change together (a bulk publish or an import), and once more when a change comes in while it runs. A block that cannot be filled, such as one naming a template folder the live site does not have, is left out of the pages and logged with its content type and folder, and the rest of the site keeps publishing. A block in an HTML comment counts for nothing, and a `count` with a fraction is rounded down. See docs/website/editable-sections.html.
- **Your own entry order.** A content type can be set to **Your own order**; **Arrange** on the entry list drags entries into place, and the list page and home page cards follow it.
- **Site info on pages.** `data-arc-site`, `data-arc-site-if` and `data-arc-site-loop` print the site's name, email, phone, address, logo, social links, standard pages and the year from Settings, About, in the header, footer, home page, templates and static pages. About gains a public **Phone**, published as `telephone`.
- **FAQ custom field.** Repeating questions and answers, with FAQPage structured data on the page.
- **Contact form** (feature `contact`, on by default). `<form data-arc-contact-form>` on any published page, spam checks, a **Messages** inbox and an alert to admins (`admin_contact_message`). New functions `submitContactMessage` and `onContactMessageCreated`, a `ContactMessages` collection with its rules and index.
- **Standard pages.** A built-in **Info Pages** type at `/info` with About, Contact, FAQ, Privacy Policy, Terms and Cookie Policy as drafts, created by the setup wizard or **Add standard pages**. A new `info` template folder shows a map, questions, contact details and the contact form per page. Structured data type **Web page**.
- **Page layouts.** A template folder may hold layouts, `detail-{name}.html`, and an entry picks one with **Layout** in the editor (shown only when its folder has one); list and card templates are unchanged. A layout the live site lacks falls back to `detail.html`. Core ships a Contact layout for the standard pages (intro, map beside the address, contact boxes beside the form), a new **Info boxes** field on Info Pages, and a new Contact page starts with both.
- **Entries of another type on a detail page.** A loop container in a detail template or layout with `data-arc-items-src="{type}"`, such as `<ul data-arc-loop="items" data-arc-items-src="events" data-limit="3">`, shows that type's published entries as cards (the list page's bindings), 6 unless `data-limit` says otherwise and at most 50, in the type's order and the page's language, never the page's own entry. Several per page, each with its own rows. Filled when the page is published and when the app draws it; when an entry of the shown type changes or the type is arranged, the pages that show it are rebuilt in a release of their own (new `items-from` publish queue action). The rebuild coalesces per type like the whole-site republish, reads the shown entries once for all its pages, leaves out a page whose entry was unpublished while it ran, goes on in a new run when there are more pages than fit in one, and is skipped when the same change republishes the whole site. A loop in an HTML comment counts for nothing. See docs/features/templates.html.
- **Word the signup confirmation your way.** A form can carry `data-waitlist-success-title`, `data-waitlist-success-text`, `data-waitlist-existing-title` and `data-waitlist-existing-text` (with `{name}` and `{email}`), and a strings file for the default language (`src/custom/site/strings/en.json` for English) now works like any other: its `signup_*` keys reword the panels and its other keys the page, on every page in that language, static pages included, and in the app. New key `signup_success_text`. See docs/website/forms.html.
- **`npm run forms:remove-referrals`** counts, and with `-- --apply` deletes, the referral records signup forms of older versions left behind; each names the person who was referred. See docs/features/forms.html.
- **Previous beside Next in the editor.** An entry picks the entry before it in a series as well as the one after it, with the same search box, by mouse or by keyboard (arrow keys, Enter and Escape; the box is a labelled combobox). The entry picked in one is not offered in the other. Both are saved with the draft, published and kept in version history; a restore puts them back as the linked entries are now and drops a link to an entry deleted since. Picking Next makes this entry the other one's Previous, and picking Previous makes it the other one's Next, unless that entry already links elsewhere; removing or changing a link removes the link back while it still points here. A save writes only the links changed in the editor, so an editor open in another tab never undoes a link set or removed elsewhere, and a link back that failed is tried again on the next save. Renaming an entry, or changing its slug, updates the copy kept by entries that link to it. The other entry's draft shows as Edited until it is published again. See docs/features/content.html.
- New translation keys: `admin.contents.editor.previous_content_label`, `previous_content_hint`, `next_content_label`, `series_search_placeholder` and `series_remove`; `next_content_hint` is longer.

### Changed

- **A function's cold start loads only its own file.** After each functions build, `functions/lib/function-map.json` names the file of each function, and an instance loads only that one (`functions/src/load-functions.ts`). See docs/app/functions.html#cold-starts.
- **A smaller first script.** Angular Material, the animation engine, Firebase Storage, Angular's forms and the feedback panel are no longer in the script every page loads first: 1,736 KB (489 KB compressed) became 1,244 KB (377 KB compressed). Storage loads through `ArcStorage` (`src/app/core/config/arc-storage.ts`) the first time something uses it, the paginator's translated labels come with the admin, and the feedback button once the page is idle.
- **The button that collapses the side menu is always in reach**, in the admin and the member area. In the admin it no longer slips off the panel beside a long site name or a wide logo, and it stays at the top while the menu scrolls; the member area gets the same button, collapsing its menu to icons. On a phone each area's menu bar stays at the top of the screen, closing the admin menu there no longer changes the wider screen's choice, a first visit opens the admin menu instead of collapsing it, and the admin follows a window resized across phone width. A page's own sticky bar uses `--arc-admin-sticky-top` to sit below the phone bar. See docs/admin/overview.html and docs/members/overview.html.
- **The install files ship with no Firebase project.** `src/environments/environment.ts` and `environment.prod.ts` have empty web settings, and `arc-install.ts` is `{}`. A copy that has not been set up stops at `npm run dev` or `npm run build` with "No Firebase project configured: run npm run arc:configure", instead of talking to Arc CMS's own project. Arc CMS never changes the values in these files again; when it needs a new key in one, this changelog names it.
- **`npm run dev` and `npm run build` use the `default` alias** in `.firebaserc` when `arc:configure` has written its `firebase-web.<id>.ts`, and print the project as they start. They fall back to the environment files only when there is no such file. `ARC_PROJECT` still wins.
- `firebase-web.<id>.ts` now carries the project's install settings (`arcInstall`) too; an entry in `arc-install.ts` still wins.
- With the `seo` feature off, `npm run seed` no longer writes robots.txt, the sitemap, llms.txt, llms-full.txt or the feeds, and the next website deploy removes the ones already on Hosting.
- The callable check (`npm run deploy -- --probe`, `functions/scripts/check-callable-access.sh`) reads the functions build without `GCLOUD_PROJECT`, checks the deploy's project and its functions region by default instead of a fixed project, and says it checked nothing (exit 2) rather than reporting callables as blocked when it cannot read the build.
- On a translated page, only links to pages that exist in every language take the language prefix: the home page, search and public content types. Sign-in, the member area, an app's own pages, static pages and files keep their address, and a stray `/hi/signup` redirects to `/signup`.
- The app's own files in `src/custom/site/assets/` are linked with their version (`/site/home.css?v=…`) on published pages, in the preview and in `url()` of the app's stylesheets, so a changed file reaches returning visitors.
- Publishing reads templates and site files from the live site's `/_site/`; template overrides stored in Firestore are no longer read.
- The build no longer prerenders or builds a server bundle.
- **`firebase-functions` is now 7.4.0** (was 7.1.0), which clears the Firebase CLI's "out of date" warning on deploy. No code changes in an app. After merging, run `npm install --prefix functions` and redeploy all the functions.
- Dependencies refreshed with `npm audit fix` (lock files only, no version range changed): no critical advisories left, root down from 69 to 32 advisories and `functions/` from 52 to 20. Run both installs after merging.
- **The Firebase CLI is pinned in the root `package.json`** instead of `functions/package.json`. Functions deploys no longer install it (467 fewer packages, `functions/` advisories down to 11), and the npm scripts still run the pinned copy. A CI workflow copied from docs/app/ci.html can drop the step that adds `functions/node_modules/.bin` to `GITHUB_PATH`. An app that added `firebase-tools` to `functions/package.json` itself should remove it there.
- `npm run deploy` keeps the published pages when it deploys the website: the build goes to a preview channel, then one live release holds the build and the published pages. Never deploy the website with a plain `firebase deploy --only hosting`.
- Publishing keeps every file of a site past 1000 files (the live file list is now read page by page).
- `main.css` styles only the body, header and footer. The old marketing page's styles are in `docs/examples/arc-cms-home.css`. Its global `section { padding: 100px 0 }` rule is gone too.
- The published home page republishes itself when Settings it shows change (About, the site address, languages, the powered-by line).
- Signups from the published home page record the same metadata as the app's forms, and someone already on the list sees "Welcome back".
- `arc-site.js` runs on every published page (content, list and static pages too), so signup and contact forms work anywhere on the site.
- The signup terms notice, the contact form's privacy line and the cookie banner link to the published standard pages (`/info/terms`, `/info/privacy-policy`, `/info/cookie-policy`) when they exist.
- The default footer lists the published standard pages and a copyright line instead of the Documentation, GitHub and Community links. Its `main.css` rules apply only to the site footer, so a `<footer>` inside a card or dialog keeps its own look.
- The About setting **Profiles elsewhere (sameAs)** is now **Social and profile links**.
- **`npm run test` type-checks the app and the functions**, and **`npm run typecheck`** runs that check alone (`scripts/typecheck.mjs`). Vitest does not check types, so a type error used to pass the suite and fail only at `npm run build` or a deploy. The admin SMS settings page had one such error, which stopped the production build; it is fixed.
- **The core specs pass in an app with its own website.** The strings, template, layout and home page specs read the site Arc CMS ships (`coreSiteManifest()` in `src/test/core-site.ts`) instead of the built manifest, so a strings file for the default language (`src/custom/site/strings/en.json`), or a template or layout of the app's own, no longer fails them. The `arc:own-site` end to end tests all get the long timeout. See docs/operations/testing.html.
- On a site whose default country code is `+1` or `+7`, a number typed without `+` that starts with that digit (every Kazakh mobile starts with 7) was read as already carrying the code: `701 123 45 67` became `+7011234567`. Both twins of `normalizePhone` now need all eleven digits for those codes. In Russia, Kazakhstan and Belarus, a number typed with the domestic `8` in front of it beside the country chip is read correctly.
- New member translation keys: `member.phone_country.*`, `member.auth.identifier_error.phone_start_choose` and `phone_not_allowed`; `phone_start` is shorter.
- **Sign-in codes: waits and limits.** Choosing Change number and coming back to the same number (or address) within the code's 10 minutes goes straight to the code boxes, with the Resend countdown carrying on, instead of "Please wait 39s" and a live Resend button. A "please wait" from the server starts the countdown. The server checks the one-minute wait before the hourly limits, and a send the provider refuses gives its count back, so only codes actually sent count. At the limit the page says when to try again ("Try again after 5:42 PM"). The profile's add-a-number and add-an-email steps behave the same. See docs/features/sign-in.html.
- **One sign-in code at a time.** Asking for a code again while the last one still works (not used, not expired, under 5 wrong tries, sent in the last 30 minutes) sends the same code with another 10 minutes, by SMS and by email, so a person never holds two messages with different codes; the page says "We sent the same code again." Wrong tries are no longer reset by a resend. The code is kept sealed (AES-256-GCM, key derived from the server's secret in `_system`) beside its hash; codes stored before this update get a new code on the next request. Functions `requestPhoneOtp`, `requestSignupOtp` and `requestEmailLinkOtp` reply `sameCode: true` when they resent one.
- **Sign-in messages from the server are in the member's language.** Every refusal the sign-in functions send a member carries `details.reason` and its numbers, and the page shows `member.auth.server_error.<reason>`; the server's English is only a fallback.
- `consumeRateLimit` (app kit) takes an optional fifth argument, `reason`, and its refusal carries `details.reason` and `details.retryAfter` (seconds). Existing calls work unchanged.
- New member translation keys: `member.auth.server_error.*`, `member.auth.code_already_sent` and `member.auth.code_sent_again`.
- **A hand-written page's own styles win over the site's, as on the home page.** Publishing a page from `src/custom/site/pages/` now puts Arc CMS's stylesheets (Bootstrap, Font Awesome, `main.css`, your `site.css`) first in its `<head>`, right after `<meta charset>`, and the page's own `<style>` and `<link>` tags after them. Before, they came last, so a rule in `site.css` beat the page's own rule for the same class (a home page `.hero` in `site.css` reshaped a page's own `.hero`). Republish and check any page that relied on the site's rule winning. See docs/website/static-pages.html.

### Removed

- **Signup forms have no referrals, queue position or leaderboard any more.** A form on any page shows a tick, "You're on the list!" and the person's address, or "You're already on the list."; the form's own page `/waitlist/{form}` does the same. Gone:
  - the **Gamification** switch, the referral box on the code step, the position, signup count, referral code and link and leaderboard button in the panels, and `?ref=` handling;
  - the `/leaderboard` and `/user/{form}/{member}` pages: their links in emails already sent now open `/waitlist/{form}` (or `/`);
  - the admin's referral numbers, Top Referrers, Position and Referrals columns and CSV columns, the user detail's referral section, the form list's Leaderboard action and the dashboard's Referrals column;
  - the functions `creditReferral`, `getPublicLeaderboard`, `getPublicMemberView`, `getOptimizedLeaderboard`, `migrateWaitlistedUsers`, `onReferralCreate`, `onReferralUpdate` and `onWaitlistUserDelete`;
  - the merge tags `##POSITION##`, `##REFERRAL_CODE##`, `##REFERRAL_LINK##` and `##LEADERBOARD_LINK##` (they now come out empty), and the analytics events `referral_code_used`, `referral_link_copy` and `leaderboard_view`;
  - the two `totalReferrals` indexes, and the rules that let a visitor create referral records or write `leaderboardLink` and `referredBy` on a member.
- `joinForm` returns only `memberId`; `finalizeFormSignup` returns `totalSignups`, `emailVerified` and `alreadyConfirmed`. New members get no `referralCode`, `referralLink`, `leaderboardLink`, `queuePosition`, `totalReferrals`, `maskedEmail` or `waitlistedUserId`; members from before keep theirs, unread.
- A visitor can no longer change a form's `totalSignups`: only an admin and Cloud Functions write a form document.
- **Panel classes.** Kept: `.waitlist-verify-step`, `.waitlist-success-step`, `.waitlist-existing-step`, `.waitlist-otp-input`, `.waitlist-verify-btn`, `.waitlist-resend-btn`, `.waitlist-back-btn`, `.waitlist-inline-message`. New: `.waitlist-success-icon`, `.waitlist-success-title`, `.waitlist-success-text`, in both confirmations. Gone: `.waitlist-stat-number`, `.waitlist-leaderboard-btn`, `.waitlist-copy-input`, `.waitlist-copy-btn`, `.waitlist-referral-input`. CSS that hid the gamified parts of the panels can go.
- The default welcome email is a plain confirmation. A form whose welcome is still exactly the old default, with its referral and leaderboard buttons, gets the new one the next time it is used; an edited welcome is left alone.
- The signup panel keys `signup_position`, `signup_total`, `signup_move_up`, `signup_move_up_body`, `signup_referral_code`, `signup_share_link`, `signup_leaderboard`, `signup_referral_placeholder`, `signup_copy` and `signup_copied`, and the admin key `admin.dashboard.col_referrals`.

### Fixed

- **A burst of changes republishes the whole site once.** Each change that needed a whole-site republish (a standard page's footer link, About printed on other pages, **Republish website**) added a queue item of its own, so several close together ran full rebuilds side by side, and their Hosting releases, each built from the release before, could drop each other's pages. A whole-site republish is now one queue item (`_publish_queue/redeploy-all`): requests while it waits join it, a request while it runs makes it run once more, and it is cleared when it ends. A site with more pages than fit in one run of the function goes out in parts, each run going on from where the last stopped, and a run that fails, its release included, runs again from the same part, up to 3 runs in a row. A run the function died in is run again by the new scheduled function `recoverPublishQueue` (every 10 minutes), with the changes it was asked for meanwhile; `items-from` rebuilds work the same way. See docs/reference/cloud-functions.html.
- **Two releases close together no longer drop each other's pages.** Separate queue items, such as an entry publish and the `items-from` rebuild or whole-site republish it starts, each released to Firebase Hosting on their own, and each built its version from the live version it started on, so the one released last dropped the files the other had added. Releases to a site now run one at a time behind a lock (`_hosting_releases/{siteId}~lock`). A release that waited builds on the version released while it waited, even before the Hosting release list shows it. A lock left by a function that died mid-release is taken over after 10 minutes, and a release that waits more than 3 minutes fails with `HOSTING_RELEASE_BUSY` instead of racing. Every release takes the lock, robots.txt, llms.txt, the sitemap and the feeds included, and the seed now releases those together, in one release. A publish waits a second time before it is marked failed; a whole-site republish or `items-from` rebuild waits only while its release still fits in the function's 540 seconds, and runs again when it could not release. See docs/reference/cloud-functions.html.
- **Editors can only add publish queue items of the shape the admin app sends.** The rules let staff write any document in `_publish_queue`, so one could write `redeploy-all` or `items-from--{slug}` as running with a start in the future and block every whole-site republish or rebuild. Staff may now only create items with `action`, `contentTypeSlug`, `docId` and `timestamp`, never with those ids, and never change or delete one. A queue item or release lock whose start is more than a minute in the future is taken for dead. The admin app no longer tries to clear old queue items before a publish, which the rules never allowed.
- Deleting a field from the middle of a content type's field list, on the add or edit screen, removed the last field from the screen while the form dropped the right one, and later typing went to the deleted field. The screen now removes the field you deleted, and the form counts the deletion as an unsaved change. Deleting a pricing tier on the Products screen had the same fault and is fixed the same way.
- Picking a Next entry on a new, unsaved entry wrote the placeholder id `temp-id` into the other entry's Previous, a link to nowhere. The link back is now written only after the first save, and an old `temp-id` link is replaced the next time it is set.
- Removing or changing Next left the old entry's Previous pointing here; it is now cleared. A Previous someone set by hand is no longer overwritten.
- Saving an entry no longer rewrites every entry whose Next points at it when nothing they show changed, which marked them all Edited.
- **Previous and Next links work on published pages.** The Articles and Manuals detail templates linked them with `previousContent.url` and `nextContent.url`, which only the app sets, so every published page had empty links. They now build the link from `langPrefix`, `contentTypeSlug` and the entry's `slug`, and their Previous and Next labels follow the page's language without losing the arrow.
- After a publish, the editor stopped waiting for the result after 60 seconds, so a publish that waited for another release showed no result. It now waits up to 10 minutes, longer than the publish function may run.
- **`npm run dev` shows a hand-written page as it is published.** At `/p/{name}` the app kept only the page's `<body>`, so the page's own stylesheets, `<style>` blocks and fonts were missing and its scripts never ran. The app now adds them after its own styles while the page is open, takes them away when you leave it, and runs the page's scripts once the page is drawn, in the order written, each script with a `src` loaded before the next. See docs/website/static-pages.html.
- At `/p/{name}` in the app, a page left while its strings or the site's details were loading, for another route or another `/p/` page, still added its styles and ran its scripts afterwards, and nothing took them away. A page left before it is drawn now adds nothing. A `nomodule` script is skipped, as browsers with modules skip it; with a `src` it held up every script after it. `/p/constructor` and other names every object has were fetched as if the site had such a page; they now go to the not-found page.
- **Card blocks in the header and footer made the app's pages heavy.** In the pages the app draws, the footer was drawn again as the page's strings, the site's details, its standard pages and the public content types arrived, and each time its card block was mounted anew: it flashed and read every content type and 50 entries again, about five times per page view, and its query of the content types could cancel the content page's own. A block now keeps its component while it is drawn the same, reads only its own type and its `count` entries, once, and uses stores of its own. One page view with one footer block went from 10 reads (5 of every type, 5 of 50 entries) to 2 (its type, 4 entries). The docs' `footer-links` example put the loop on the `<li>`, which drew every link in one item; it is on the `<ul>` now. See docs/website/editable-sections.html.
- In the app, a card block's `count` that was negative or a fraction was not clamped (`-2` showed up to 48 cards where the published page shows 1). It now follows the publish side's rule: a whole number from 1 to 50, else 4. See docs/features/templates.html.

### For apps upgrading

1. Merge the new version. If your copy edited files in `public/`, run `npm run arc:own-site`, then `npm run arc:own-site -- --write` (docs/website/move-your-site.html).
2. Check your own templates and pages for the old marketing classes (`.hero`, `.feature-card`, `.cta-primary`, `.section-headline` and the like) and for sections that relied on the `main.css` padding. `arc:own-site` brings the old styles back for a migrated home page only; elsewhere, copy the rules you use from `docs/examples/arc-cms-home.css` into `src/custom/site/site.css`.
3. Search your own templates in `src/custom/site/templates/` for `previousContent.url` and `nextContent.url`. They are empty on published pages: write the link as `href="{{ langPrefix }}/{{ contentTypeSlug }}/{{ nextContent.slug }}"` (and the same with `previousContent`), as the shipped Articles and Manuals templates now do.
4. Run `npm run arc:configure` once, so `arc-install.ts` names your hosting site.
   - The merge conflicts in `src/environments/environment.ts`, `environment.prod.ts` and `arc-install.ts` if your copy filled them in: Arc CMS emptied them. Keep your own version of all three (`git checkout --ours <file>`).
5. Run `npm run typecheck` and fix any type error it reports in your own pages or functions: `npm run test` now fails on them. They would already have failed your production build.
6. If your app's own pages write to `_publish_queue`, check them before deploying the rules: the app may now only create queue items, with exactly `action`, `contentTypeSlug`, `docId` and `timestamp` and an action Arc CMS knows, and never read, change or delete one. Use `PublishQueueService` (`enqueue`, `redeployAll`, `reorder`) instead of writing the collection yourself. Functions are not affected: the Admin SDK skips the rules.
7. If a function of your own in `functions/src/custom/` releases files to Hosting, make it call `deployBatchToHosting()`, never the Hosting API directly, so it takes the release lock, and keep its `timeoutSeconds` at 540 or below (or pass `deployBatchToHosting()` a `deadline` well inside it). See docs/reference/cloud-functions.html, Releases to Hosting.
8. If your app has its own member languages, add the new member keys (`member.phone_country.*`, `member.auth.identifier_error.phone_start_choose`, `phone_not_allowed`, `member.auth.server_error.*`, `member.auth.code_already_sent`, `member.auth.code_sent_again`) to `src/custom/i18n/{lang}.json`; the member language check names any that are missing.
9. If your app has an admin language of its own (a `src/custom/i18n/{lang}.json` for a language Arc CMS does not ship), add the new editor keys `admin.contents.editor.previous_content_label`, `previous_content_hint`, `next_content_label`, `series_search_placeholder` and `series_remove`, and translate `next_content_hint` again: it now says the other entry links back. Until then those words show in English. If your `src/custom/i18n/en.json` rewords `next_content_hint`, check that it still fits.
10. Deploy everything (`npm run deploy`), then republish (`npm run seed:prod`). If your install used signup forms, deploy the website before the functions (the old form page needs a function this version deletes), and deploy all the functions, not a targeted set: that deletes the referral and leaderboard functions. Then run `npm run forms:remove-referrals` and, if it finds records, `npm run forms:remove-referrals -- --apply`. Check each form's welcome email for referral or leaderboard buttons you added yourself, and remove any `##POSITION##`, `##REFERRAL_LINK##` or `##LEADERBOARD_LINK##` from your own emails. Then open Settings, SMS once as an admin: that copies the list of countries for the sign-in page.
11. Check the pages in `src/custom/site/pages/` after that republish: a page's own `<style>` and `<link>` tags now come after Arc CMS's stylesheets and your `site.css`, so the page's rule wins where both style the same class. A page that relied on a `site.css` rule winning, such as a shared `.hero`, now looks different: copy that rule into the page's own styles, or drop the page's competing rule.
12. On an install set up before the standard pages, or before page layouts, open **Content types** and choose **Add standard pages** (it adds the pages and the Info boxes field that are missing). Then pick **Layout: Contact** on your Contact page if you want the new layout. If your own footer listed the old Documentation, GitHub or Community links from Arc CMS's footer, they are gone from the default one; keep your own footer as it is.
13. The copy of an entry kept in another entry's Next (and now Previous) used to hold the entry's summary and now holds its meta description. Where the two differ, the first save of each entry after the update rewrites the copies other entries keep of it, so those entries show as **Edited** once; publish them again when convenient. Next links set before this version do not link back by themselves: to give the other entry its Previous, remove the Next and save, then pick it again and save.
14. If your app's own code injects AngularFire's `Storage` (`inject(Storage)` from `@angular/fire/storage`), use `ArcStorage` instead: `private readonly arcStorage = inject(ArcStorage);`, then `const storage = await this.arcStorage.get();` and `ref(storage, path)` as before. The app no longer provides `Storage`, so the old injection fails. If your own pages show a `<mat-paginator>` outside the admin, call `useTranslatedPaginator()` (`src/app/core/i18n/paginator-intl.ts`) in one of them for translated labels.
15. If your app has its own member languages, add `member.wait.checking`, `member.wait.still_checking` and `member.wait.no_answer`; `npm run i18n:member -- --lang=<code>` lists them. If your own callable functions take a warm-up call of their own, the sign-in page's hooks send `{ warmUp: true }`: answer it with `isWarmUp()` from the app kit.
16. After merging, deploy all the functions once: every function's start changed.
