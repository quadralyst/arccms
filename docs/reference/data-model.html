Data model

This page lists every Firestore collection and Storage path Arc CMS uses, who can read and write each one, and which feature owns it.

Where the data lives

Arc CMS keeps all its data in one Firestore database and one Storage bucket per install.

  • Database. (default), unless the install config (arccms.config.json, see arccms.config.example.json) names another with databaseId, such as arccms. The backend profile, for an install that shares its Firebase project with another app, requires a named database. See Configure a project and Sharing a Firebase project.
  • How the code picks it. npm run arc:configure writes the value to src/environments/arc-install.ts for the browser app, and to functions/.env.{projectId} as ARC_DATABASE_ID for the Cloud Functions. The browser opens the database in src/app/core/config/arc-firebase.ts. Every function uses the db handle from functions/src/init.ts, and the Firestore triggers listen on the same database. The one exception is onAppUserWritten, which watches the host app's users for the App audience.
  • Bucket and upload folder. storageBucket names the bucket (default: the one in the Firebase config). storagePrefix is one folder ending in a slash, such as arccms/, put in front of new uploads. With no prefix, uploads go to the bucket root.

How content is stored

Content has no single collection. Each content type gets three, named from the type's slug: arc_{slug}_drafts for what the editor saves, arc_{slug} for the published copy (same document id as the draft), and Tags_{slug} for its tags. Deleting a content type deletes all three. See Content below.

Firestore rules cannot match a prefix, so firestore.rules has one wildcard rule, match /{collection}/{docId}, that checks the collection name with a regular expression.

The wildcard rule applies to any collection whose name starts with arc_, Tags_ or WaitlistUserTags_. An app collection named arc_orders becomes public to read. Give app collections names without these prefixes.

Your app's collections

An app keeps its own rules in firestore.app.rules and storage.app.rules. npm run rules:build puts them into the core rules at the // @arc-app-rules line, so they can call the core helpers. See Set security rules and indexes. For how the rules are built and tested, see Security rules.

Who can read and write

The rules use a few helpers. The role comes from the arccms_role claim, never a plain role; see Roles and claims.

  • isAuthenticated() and isSignedIn(): the caller is signed in.
  • isAdmin(): the arccms_role claim is admin.
  • isEditor(), "staff" below: an admin, or the arccms_role claim is editor.
  • ownsUserRecord(userDocId): the arccms_uid claim equals that users document id.
  • isOwnUserDoc(): the users document's uid field equals the signed-in Auth uid.

In the tables below, "Server only" means no browser can read or write it: only Cloud Functions do, through the Admin SDK, which bypasses the rules. Every collection with no rule is server only too, because Firestore denies what no rule allows.

Storage

Files live in the install's bucket. The browser puts storagePrefix in front of media, imported files and feedback files, so with arccms/ the media library writes arccms/mediaImages/.... Profile photos in avatars/ always go to the bucket root. The rules accept both forms: {prefix} below is that one folder.
