Build a website

This path takes you from an installed Arc CMS to a live content website that collects sign-ups. Follow the pages in order; each one says what to do in the admin area or the files, and links to the feature page for the detail.

What you will have at the end

  • Content types (articles, guides, case studies) that editors write and publish from the admin area, each published as a static page at /{type}/{item}.
  • Your own HTML templates for the list and detail pages and the cards of each type, with your header and footer.
  • Static pages such as the privacy and cookie policies.
  • Structured data, a sitemap, robots.txt, llms.txt and RSS feeds, written on every publish.
  • A search box in the header and a /search results page.
  • A signup form on the home page, with a verification code, a welcome email, referrals and a leaderboard. Every sign-up becomes a contact you can email.

Before you start

You need an installed Arc CMS with its first admin. If you have not done that yet, follow Install, Configure a project and Create the first admin. The first-run wizard creates an Articles content type and a default signup form, so you do not start from nothing.

Have these ready:

A list of your pages and their fieldsYou turn it into content types in the next two pages.
Your design as HTML and CSSTemplates are plain HTML fragments; you add Arc CMS attributes to them.

The steps

  1. Plan your content: decide what is a content type, a static page or a form, and what each URL looks like.

  2. Define content types: create them in the admin area with their fields.

  3. Design templates: give each content type its list and detail layout.

  4. Build your home page: your front door, with your own design, animation and signup form.

  5. Write static pages: the legal pages and anything else that rarely changes.

  6. Brand the sign-in page: your name, logo, words and colours where people sign in.

  7. Manage media: set image sizes and upload images.

  8. Add authors and tags: bylines and topics.

  9. Get found by search engines and AI: fill in your site identity and write pages that get quoted.

  10. Publish in more than one language: only if you need it.

  11. Add search: choose what visitors can search.

  12. Collect sign-ups: set up the form, its emails and where sign-ups land.

  13. Choose your website's features: switch off what a website does not use.

  14. Launch checklist: check everything before you point your domain at it.

Recommended features

A content website with lead generation uses content, templates, media, authors and tags, SEO, search, signup forms, audience and email. Keep them all on. Switch off payments and SMS unless you sell or use phone sign-in; Choose your website's features shows how. The full list is in All features.

How you work

Most of the work happens in the admin area at /admin. The rest is your website's own files, which live in one folder, src/custom/site/. It is part of the custom space: Arc CMS never ships or changes anything in it, so an upgrade never conflicts with your site.

File or folderWhat it holds
src/custom/site/home.htmlThe home page: one HTML file with your own styles, scripts and animation, published in every language (Build your home page)
src/custom/site/templates/The partials, list and detail layouts of your content types, one folder each
src/custom/site/header.html, src/custom/site/footer.htmlThe site header (menu, search box, language switcher) and footer
src/custom/site/pages/Static pages such as your privacy policy and terms
src/custom/site/sign-in.htmlThe brand panel of the sign-in page
src/custom/site/site.cssStyles for every public page and the sign-in page
src/custom/site/strings/The translations of your header, footer and templates
src/custom/site/assets/Images, scripts and fonts, served at /site/... and linked with their version, so a change reaches every visitor
src/custom/features.tsThe features you switch off

Every file is optional. Where you have none, Arc CMS's own is used (from public/_site/), and it keeps improving with each upgrade. Where you have one, yours replaces Arc CMS's. The build puts the two together and serves them at /_site/, and the app and the publish functions both read from there, so what you see locally is what publishes. The full list is in Design templates and Use the custom space.

None of these is a core file, so npm run check:core stays clean and an Arc CMS upgrade never conflicts with your site. All of them are plain HTML, CSS and JavaScript: there are no special rules for {, } or @.

Run the site locally with npm run dev while you build; it reads and writes your real Firebase project (see Run it locally). Publishing an item puts its page on the live site straight away. Changes to files reach the live site when you deploy the website (see Deploy).
