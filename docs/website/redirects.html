Redirect old addresses

When Arc CMS replaces an existing site, the old addresses are in search results, bookmarks and other people's links. List each one with its new page in src/custom/site/redirects.json, and Firebase Hosting sends visitors and search engines on with a 301 (moved for good) or 302 (moved for now).

Write the file

The file is a list of redirects in Firebase Hosting's own format. It is part of the custom space, so you never edit firebase.json, which is a core file. Without the file there are no redirects of your own.

[
  { "source": "/services-web-designing.html", "destination": "/services/web-designing", "type": 301 },
  { "source": "/news/:post*", "destination": "/blog/:post", "type": 301 },
  { "source": "/old-shop/**", "destination": "https://shop.example.com", "type": 302 },
  { "regex": "^/blog/(?P<slug>[^/]+)\\.html$", "destination": "/blog/:slug", "type": 301 }
]
FieldWhat it holds
sourceThe old address, starting with /. It can be a pattern: * matches within one part of the path, ** any number of parts, :name captures one part and :name* the rest of the path, for use in destination
regexInstead of source: a regular expression in RE2 syntax. A named group, (?P<slug>...), is used in destination as :slug; an unnamed one as :1, :2
destinationThe new address: a path on this site starting with /, or a full https:// or http:// URL
type301 for a page that moved for good, which search engines follow and pass the old page's standing to; 302 for a move that is for now. Without it, Hosting sends 301

How Hosting uses them

  • Yours come first. The deploy puts your redirects ahead of Arc CMS's own (/p/{name} to /pages/{name}), in the order you wrote them, and Hosting answers with the first one that matches. So list the specific ones before the wide patterns, and know that a redirect of yours can take over an address Arc CMS's own would otherwise send elsewhere, such as an old /p/about.html.
  • A redirect wins over a file. Hosting checks redirects before it looks for a file, so a redirect whose source matches a published page hides that page. Redirect only addresses your new site does not use.
  • They are live with the website. The redirects change only when you deploy the website (npm run deploy, choosing the website or everything, deploy:dev, deploy:prod or CI). Publishing a page does not change them.

What is refused

npm run dev, npm run build and every website deploy check the file, and stop with a message that names each bad redirect by its number and its source. A deploy stops before anything is built or deployed. The checks:

  • the file must be valid JSON and hold a list;
  • each redirect has a source or a regex, not both, and a destination that is a path or an http(s) URL;
  • type, when given, is 301 or 302; any other field is refused, so a misspelt one never goes unnoticed;
  • no source or regex appears twice, since Hosting would only ever use the first, and no redirect sends an address to itself;
  • no redirect catches an address Arc CMS needs: /admin, /assets/, /_site/, /site/, /_arc/, /__/, /unsubscribe, /email-preferences, and the search engine files /sitemap.xml, /robots.txt and /llms.txt. A pattern as wide as ** or /:page catches /admin and is refused too, and so is one for every old .html address (**/*.html, ^/(.*)\.html$): it would also take the site's own templates and pages under /_site/. Limit it to the old site's folders or to one level, such as /blog/**/*.html or /:page.html.

Try them

npm run dev checks the file but does not follow the redirects: only Firebase Hosting does. Deploy the website to your development project and ask for an old address. The answer should be 301 or 302 with the new address as its location:

curl -I https://your-dev-project.web.app/services-web-designing.html

Where they go

A website deploy uploads the build with the project's Hosting config, from its firebase.{projectId}.json when npm run arc:configure wrote one, else from firebase.json (see Configure a project). With redirects of your own, the deploy writes a copy of that config with your redirects first, firebase.{projectId}.website.json, uploads the build to the arc-deploy preview channel with it, and removes the copy. The live release takes the channel's config, so your redirects go live with the build (see Publish the pages again). The other parts of a deploy, such as functions and rules, do not use them.

Plain firebase deploy or firebase hosting:channel:deploy reads only firebase.json, so it leaves your redirects out. Deploy the website with npm run deploy.
