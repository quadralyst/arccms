App accounts

Some people your app serves have no email and no phone: staff on a shared device, a child, a kiosk. Your own Cloud Function can still give each of them an Arc CMS account, so the member area, the guards and your rules treat them as signed in like anyone else.

What such an account is

  • A Firebase Auth account with only a display name.
  • A users record with email and phone set to '', Arc CMS role user, isActive: true, by: 'app' and selfService: false. The admin's users list shows it with an App account badge, and an admin can edit it without adding an email.
  • The usual claims, arccms_uid and arccms_role (see Follow the account contract), plus any of your own.
  • Locked: the person cannot change the account themselves (below).

Arc CMS sends such a person no email or SMS, since it has neither address. The admins get no "just signed up" alert for it, because your app created it; the user.signed_up event is still sent. The role is always user: an app helper never makes an Arc CMS admin. Your app's own roles go in your claims.

Create an account and sign the person in

How the person proves who they are is your app's choice. The usual one is a PIN (see PINs for your app), checked in your own callable, which then returns a sign-in token:

// functions/src/custom/staff.ts
import { onCall, HttpsError } from 'firebase-functions/v2/https';
import { createAppAccount, isArcAdmin, issueSignInToken } from '../app-kit/index.js';

/** A manager adds a member of staff. */
export const addStaff = onCall(async (request) => {
  if (!isArcAdmin(request.auth?.token)) throw new HttpsError('permission-denied', 'Managers only.');
  const { name, siteId } = request.data ?? {};
  const { uid } = await createAppAccount({ displayName: String(name ?? ''), claims: { site: String(siteId), staffRole: 'front-desk' } });
  return { uid };
});

/** Signs a member of staff in once your own check has passed. */
export const staffSignIn = onCall(async (request) => {
  const uid = String(request.data?.uid ?? '');
  // ... check the person here (a PIN, a badge), and refuse if it fails ...
  return { token: await issueSignInToken(uid) };
});

Add both names to functions/src/custom/public-callables.txt (see Write your own Cloud Functions). In the browser, exchange the token:

import { signInWithCustomToken } from '@angular/fire/auth';

const { token } = (await arcCallable<{ uid: string }, { token: string }>(this.functions, 'custom-staffSignIn')({ uid })).data;
await signInWithCustomToken(this.auth, token);

From then on the person is signed in: the member area and userGuard let them in, and their token carries arccms_uid and your claims from the first sign-in.

Your own claims

mergeAppClaims(uid, patch) adds or changes your claims on any account, an app account or not:

await mergeAppClaims(uid, { staffRole: 'manager', perms: ['approve', 'cancel'] });
await mergeAppClaims(uid, { site: null }); // removes your "site" claim
  • It merges: Arc CMS's claims and every other claim stay.
  • It refuses a name starting arccms_ and the names Firebase reserves (sub, firebase, exp and the like).
  • All of an account's claims together may take 1000 bytes as JSON. It refuses before writing when they would pass that.
  • A new value reaches the browser at the person's next token refresh (within the hour), or at once after getIdToken(true).

Firebase cannot merge claims in one step: a write reads the claims, then replaces them all. So Arc CMS's own claims writes and mergeAppClaims() take turns on each account: a write holds a short lease (15 seconds) while it reads, writes and reads back, and another write on the same account waits for it. A write that changes nothing takes no lease. Two writes through Arc CMS keep each other's claims, with one exception: a write still running when its lease runs out can race the next one, and is then read back and redone if its claims are missing.

A program outside Arc CMS that calls setCustomUserClaims on the same accounts takes no lease, and can still overwrite them. Use mergeAppClaims() for all of your claims.

Locked by default

An app account belongs to your app, not to the person using it. So it is locked: the person cannot change it, and Arc CMS's server and rules refuse each try, whatever the browser sends.

  • No new name or photo, and no new email, phone, Google sign-in, password or PIN.
  • No deleting it. deleteMyAccount refuses it even right after a sign-in; your app deletes it with deleteAppAccount().
  • It never becomes the site's first admin.
  • No account, locked or not, can change its own by or selfService.

It still signs in with your token, reads its own record, gets its claims refreshed and keeps settings that are not its identity, such as a language. Your own functions are not affected: they use the Admin SDK, which the lock does not apply to. A manager renaming someone:

import { db, owner } from '../init.js';

await owner.updateUser(uid, { displayName: name });
await db.collection('users').doc(userDocId).update({ name, modifiedAt: new Date() });

To let one person change their own account like any member, create it with selfService: true:

await createAppAccount({ displayName: 'Anna', selfService: true });

Accounts made before the lock existed have no selfService field, so they are locked too.

The member pages

By default a locked account can open the member pages (/user/... and /account, see Build the member area). Its profile shows the name and photo with nothing to change: no sign-in methods, no password and no delete. To keep locked accounts out of those pages, say so in src/custom/app-accounts.ts:

import type { AppAccountChoice } from '../app/core/app-accounts/app-account-lock';

export const CUSTOM_APP_ACCOUNTS: AppAccountChoice = { memberPages: false };

A locked account that opens one then goes to its home page from src/custom/home.ts, or to the site's home page when that home is itself a member page. The member menu hides those pages for it. Your own pages are not affected: a route with userGuard still lets it in.

What the browser can still do

Firebase lets a signed-in browser link Google, a password or a phone to its own sign-in account without asking Arc CMS's server. Refusing that needs Identity Platform's blocking functions, which Arc CMS does not use. Arc CMS hides every control that does it for a locked account, and the users record never follows such a link. When the person later signs in that way, the server sees a locked account signed in without your token: it takes that way in off the account, ends all its sessions and refuses. Until then that sign-in carries your claims, so a rule that trusts a claim alone trusts it too. Where that matters, also check that the token came from your app: request.auth.token.firebase.sign_in_provider == 'custom'.

Sessions

revokeSessions(uid) signs the person out on every device: their refresh tokens are revoked, so each session ends at its next token refresh, within the hour. Use it when a member of staff leaves or a device is lost. They can sign in again as usual afterwards.

Delete an account

deleteAppAccount(uid) deletes the person's users record. Arc CMS's account deletion then does what it does for anyone (see Follow the account contract): it ends their access, deletes the sign-in, their PIN and their data under the record, and last emits user.deleted with userId (the Auth uid) and data.userDocId. Clean up your own data from that event:

export const onStaffDeleted = onDocumentCreated(arcDocument('AppEvents/{id}'), async (event) => {
  const e = event.data?.data();
  if (e?.['type'] !== 'user.deleted') return;
  await removeShifts(e['userId']); // your own data, keyed by the Auth uid
});

Empty email and phone never match

Many records with an empty email or phone could match a lookup by an empty value. Every Arc CMS lookup by exact email or phone checks for an empty value first and finds nothing, and a test fails on a new one that does not. Do the same in your own functions: never query where('email', '==', x) without checking that x is not blank.
