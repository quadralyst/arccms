App accounts

Some people your app serves have no email and no phone: staff on a shared device, a child, a kiosk. Your own Cloud Function can still give each of them an Arc CMS account, so the member area, the guards and your rules treat them as signed in like anyone else.

What such an account is

  • A Firebase Auth account with only a display name.
  • A users record with email and phone set to '', Arc CMS role user, isActive: true and by: 'app'. The admin's users list shows it with an App account badge, and an admin can edit it without adding an email.
  • The usual claims, arccms_uid and arccms_role (see Follow the account contract), plus any of your own.

Arc CMS sends such a person no email or SMS, since it has neither address. The admins get no "just signed up" alert for it, because your app created it; the user.signed_up event is still sent. The role is always user: an app helper never makes an Arc CMS admin. Your app's own roles go in your claims.

Create an account and sign the person in

How the person proves who they are is your app's choice. The usual one is a PIN (see PINs for your app), checked in your own callable, which then returns a sign-in token:

// functions/src/custom/staff.ts
import { onCall, HttpsError } from 'firebase-functions/v2/https';
import { createAppAccount, isArcAdmin, issueSignInToken } from '../app-kit/index.js';

/** A manager adds a member of staff. */
export const addStaff = onCall(async (request) => {
  if (!isArcAdmin(request.auth?.token)) throw new HttpsError('permission-denied', 'Managers only.');
  const { name, shopId } = request.data ?? {};
  const { uid } = await createAppAccount({ displayName: String(name ?? ''), claims: { shop: String(shopId), staffRole: 'cashier' } });
  return { uid };
});

/** Signs a member of staff in once your own check has passed. */
export const staffSignIn = onCall(async (request) => {
  const uid = String(request.data?.uid ?? '');
  // ... check the person here (a PIN, a badge), and refuse if it fails ...
  return { token: await issueSignInToken(uid) };
});

Add both names to functions/src/custom/public-callables.txt (see Write your own Cloud Functions). In the browser, exchange the token:

import { signInWithCustomToken } from '@angular/fire/auth';

const { token } = (await arcCallable<{ uid: string }, { token: string }>(this.functions, 'custom-staffSignIn')({ uid })).data;
await signInWithCustomToken(this.auth, token);

From then on the person is signed in: the member area and userGuard let them in, and their token carries arccms_uid and your claims from the first sign-in.

Your own claims

mergeAppClaims(uid, patch) adds or changes your claims on any account, an app account or not:

await mergeAppClaims(uid, { staffRole: 'manager', perms: ['refund', 'void'] });
await mergeAppClaims(uid, { shop: null }); // removes your "shop" claim
  • It merges: Arc CMS's claims and every other claim stay.
  • It refuses a name starting arccms_ and the names Firebase reserves (sub, firebase, exp and the like).
  • All of an account's claims together may take 1000 bytes as JSON. It refuses before writing when they would pass that.
  • A new value reaches the browser at the person's next token refresh (within the hour), or at once after getIdToken(true).

Firebase cannot merge claims in one step: a write reads the claims, then replaces them all. Arc CMS reads each write back and redoes it if another write replaced it in between, so Arc CMS's claims and those set through mergeAppClaims() never lose each other. A program outside Arc CMS that calls setCustomUserClaims on the same accounts can still overwrite them; use mergeAppClaims() for all of your claims.

Sessions

revokeSessions(uid) signs the person out on every device: their refresh tokens are revoked, so each session ends at its next token refresh, within the hour. Use it when a member of staff leaves or a device is lost. They can sign in again as usual afterwards.

Delete an account

deleteAppAccount(uid) deletes the person's users record. Arc CMS's account deletion then does what it does for anyone (see Follow the account contract): it ends their access, deletes the sign-in, their PIN and their data under the record, and last emits user.deleted with userId (the Auth uid) and data.userDocId. Clean up your own data from that event:

export const onStaffDeleted = onDocumentCreated(arcDocument('AppEvents/{id}'), async (event) => {
  const e = event.data?.data();
  if (e?.['type'] !== 'user.deleted') return;
  await removeShifts(e['userId']); // your own data, keyed by the Auth uid
});

Empty email and phone never match

Many records with an empty email or phone could match a lookup by an empty value. Every Arc CMS lookup by exact email or phone checks for an empty value first and finds nothing, and a test fails on a new one that does not. Do the same in your own functions: never query where('email', '==', x) without checking that x is not blank.
