Member languages

Your members, signed in or about to sign in, can use your app in a language Arc CMS does not ship, such as German. You declare it and write the translations; Arc CMS shows it on the member screens. The admin keeps Arc CMS's own languages.

Add a language

  1. Declare it in src/custom/languages.ts:

    import type { MemberLanguage } from '../app/core/i18n/member-languages';

export const MEMBER_LANGUAGES: readonly MemberLanguage[] = [
    { code: 'de', label: 'Deutsch', locale: 'de-CH', localeData: () => import('@angular/common/locales/de-CH') },
];

    code names the translation file, label is the language's name in itself, locale is how dates and numbers are written, and localeData loads Angular's data for that locale (leave it out for an English locale). A mistake here stops npm run dev and npm run build with a message saying what to change.

  2. Translate it in src/custom/i18n/de.json, with the same keys as English. To see what is left to translate:

    npm run i18n:member -- --lang=de

    It lists every member-facing Arc CMS key and every key of your own src/custom/i18n/en.json that de.json lacks. A key you leave out shows in English, never as the key itself.

  3. Run the tests. The parity test fails naming each missing key. While a language is still being translated, add partial: true to its entry: the missing keys are then listed as a warning instead.

Members get English plus the languages you declare. Arc CMS's Hindi is offered to members only if you declare it too ({ code: 'hi', label: 'हिन्दी', locale: 'hi', localeData: () => import('@angular/common/locales/hi') }); its member keys are already translated.

Example: German for a shop's staff

An app that declared de above, with one screen of its own whose English is in src/custom/i18n/en.json:

{ "custom": { "till": { "open": "Open the till" } } }

Its src/custom/i18n/de.json translates Arc CMS's member keys and its own, with the same nesting:

{
  "member": { "auth": { "continue": "Weiter" } },
  "user": { "nav": { "dashboard": "Übersicht" } },
  "custom": { "till": { "open": "Kasse öffnen" } }
}

With only these three keys, npm run i18n:member -- --lang=de lists the rest, and the parity test fails naming them until partial: true is set. A German-speaking member then sees "Weiter" on the sign-in button, "Übersicht" in the member menu and "Kasse öffnen" on your screen, and English for every key not yet written. A language picker of your own switches it:

import { setMemberLanguage } from '../../app/core/i18n/member-language.service';

// In your component, for a button such as <button (click)="german()">Deutsch</button>
german(): void {
  setMemberLanguage('de');
}

Which language a member sees

  • Their choice on this device. Set it from your app's own picker or settings: setMemberLanguage('de'), from src/app/core/i18n/member-language.service.ts, or use() on MemberLanguageService. It is kept on the device, so a shared device shows it on the sign-in screen too.
  • On a first visit, the browser's language, when you declared it (de-AT finds de); otherwise English.
  • In the admin area (/admin), the admin's own language, always. Pages outside it use the member language.

The language picker in the page header is the admin's: once you declare member languages it shows only in the admin area, since the admin's choice does not change member pages. Members choose through a picker of your own (below).

With no languages declared, nothing changes: member screens follow the admin language as they always did.

Dates and numbers

The text switches at once. Angular's date and number pipes take the locale when the page loads, so they follow a new choice on the next load; setMemberLanguage('de', { reload: true }) reloads at once. For a value that must follow the switch without a reload, pass the locale yourself: {{ when | date: 'mediumDate' : undefined : member.activeLocale() }}. A person who opens the admin first and then a member page in the same visit keeps the admin's formats until the next load.

Which screens follow the language

Sign-in and sign-up (with email, phone and PIN, and Google), forgot password and PIN, the code steps, the profile with its sign-in methods, the account and membership page, the member area with its menu, dashboard, payments and premium pages, the install and update prompts, the feedback panel, the reload message, the page-not-found and no-access pages, and the cookie banner's own words (its "Learn more" link, and the buttons when the admin leaves their text empty). The sign-in errors Arc CMS shows itself, including Firebase's, are translated too. Messages the server sends back for a code or a PIN (a wrong code, too many tries) stay in English; see What stays in English.

Which keys are member-facing

The list is src/app/core/i18n/member-keys.ts: everything under member.*, user.* (the member area), common.pwa.* (install and update prompts), common.feedback.* (the feedback panel), common.version.* (the reload message), and a few shared keys such as common.actions.close. A test fails when a member screen uses a key the list does not cover.

Check every screen by eye

npm run i18n:pseudo -- --out=src/custom/i18n/zz.json

This writes a pseudo translation of the member keys, every word accented and in brackets. Declare { code: 'zz', label: 'Pseudo', locale: 'en-GB' }, call setMemberLanguage('zz'), and walk the member screens: any plain English left is text that is not translated yet. Remove the file and the entry afterwards.

Your own screens can be checked the same way in a spec: render them with pseudoTestingModule() from src/test/pseudo-language.ts and expect textNotInPseudo(fixture.nativeElement) to be empty. To include your own keys, pass your English: pseudoTestingModule(customEnglish), with customEnglish imported from src/custom/i18n/en.json.

What stays in English

  • Emails and SMS. The password reset email is Firebase's own: Arc CMS asks Firebase for it in the member language, which Firebase uses where it has a template for it (its wording is edited in the Firebase console). The sign-up code emails and SMS that Arc CMS sends stay in English.
  • Messages from the server about a code or a PIN, such as a wrong code or too many tries.
  • Pages of optional features: pricing and checkout, signup forms and leaderboards, notifications. An app that needs them in its language rewords their text in its own files once they have keys.
  • The published site, content and list pages included (with what they say when there is nothing to show): it follows the page's own language, through the site's strings files, not the member language. See Languages.
  • What an admin writes, such as the cookie banner's message: it is the site's own content.
  • The browser tab's title on most pages.
  • The "Powered by Arc CMS" line, which an admin can turn off in Settings.
  • The sign-in page's brand panel beside the form: it is your site's HTML (see Brand the sign-in page) and follows the site's language.
