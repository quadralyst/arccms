Take payments on a merchant's account

Each customer of your app, such as a shop, a clinic or a club, takes money from their own buyers on their own provider account. The money never passes through the site's owner. Your app never writes a provider's signing, webhooks or key storage. It calls a few server helpers from its own functions, and hears each result in one place.

This is a different need from Add payments and premium features, which sells the site's own plans through one account. No page comes with it: the screens are your app's, in its languages.

Turn it on

The feature is off unless your app asks for it, as it runs a sweep every 2 minutes. In src/custom/features.ts:

export const CUSTOM_FEATURES: FeatureChoice = {
    on: ['merchant-payments'],
};

Then deploy its four functions:

npm run deploy -- --only functions:arccms:arccms.merchantPaymentWebhook,functions:arccms:arccms.onMerchantPaymentEvent,functions:arccms:arccms.sweepMerchantPayments,functions:arccms:arccms.checkMerchantAccounts,firestore:rules

While it is off, every helper below answers { ok: false, reason: 'off' }.

Which providers

paymentConnectors() lists what your screen may offer here, with what one screen needs for any provider: the fields to ask for, which are secret, which modes, whether test and live take separate keys, whether the owner adds the webhook by hand, and what the provider can do. A field's label is the provider's name for it; show it in your own words.

A connector goes on the list only when it has passed every rule on the provider's own account (Prove a connector), so a merchant can never pick an untried one. Neither has yet: paymentConnectors() lists neither on a project until the proof is done, except where ARC_PAYMENTS_TRY says so.

Connect an account

One account for each customer of your app, named by your own id, such as a business id. One provider at a time. Your function decides who may connect, so check the owner and ask for a fresh code first:

// functions/src/custom/payment-account.ts
import { onCall, HttpsError } from 'firebase-functions/v2/https';
import { connectPaymentAccount, useFreshCodeProof } from '../app-kit/index.js';

export const connectBusinessPayments = onCall(async (request) => {
  const owner = request.auth?.token['arccms_uid'];
  const { businessId, provider, mode, fields, proof } = request.data;
  // ... check that this person owns businessId ...
  await useFreshCodeProof(request, proof, 'payment-keys');
  const answer = await connectPaymentAccount({ accountId: businessId, provider, mode, fields, by: owner });
  if (!answer.ok) throw new HttpsError('failed-precondition', answer.detail, { reason: answer.reason });
  return answer.account; // the public view: show webhookAddress to the owner
});

The provider is called before anything is saved, and a key it turns down is not saved. Clear your form whatever the outcome.

CallWhat it does
connectPaymentAccount({ accountId, provider, mode, fields, by })Connects, or replaces the keys of that mode. The account then runs in that mode. Replacing keeps the webhook address the owner already added. A different provider replaces the old one and all its keys, and gets a new address; it is refused with open-payments while a payment on the old one is open.
switchPaymentMode({ accountId, mode, by })Switches between test and live, with keys already held for that mode, after trying them. no-keys-for-mode when there are none. An open payment goes on being read with the keys of the mode it started in.
disconnectPaymentAccount({ accountId, by, force? })Tries to end each open page, then removes the keys and the address. open-payments if a page would not end; with force, those are held for a person instead, as the money may still come.
readPaymentAccount(accountId)The public view, or null.

The public view is all a page ever needs: provider, mode, publicName, last4, modesWithKeys, who connected and when, webhookAddress, keyExpiresOn, the last payment update, and problems. To let a page read it directly, add your own read rule on MerchantAccounts/{accountId} in firestore.app.rules (Rules and indexes). Admins can read it already. Only the functions write it.

Start a payment

import { startPayment } from '../app-kit/index.js';

const answer = await startPayment({
  accountId: businessId,
  amountMinor: 1250,           // CHF 12.50, in whole minor units
  currency: 'CHF',
  reference: request.id,       // your own, unique in the account
  returnUrl: 'https://your.app/paid',
  lifeMinutes: 15,             // where the provider allows it
});
// { ok: true, paymentId, pageUrl, providerId, closesAtIso, lifeFixedByProvider, existing }
// or { ok: false, reason, detail }
  • Your function names the account and nothing more. The server reads the keys itself.
  • The same reference again gives back the same open page, with existing: true. Another amount, or a reference already finished, is refused with reference-used.
  • Connect keeps a page open 2 hours whatever you ask: lifeFixedByProvider is true, and closesAtIso is when it really closes.
  • returnUrl proves nothing. The buyer can reach it without paying, so never treat arriving there as paid.
  • A reference is letters, digits, and . _ : -. Connect takes at most 30 characters.

Hear the result

Fill in functions/src/custom/payments.ts. Arc CMS ships it empty and never edits it again:

import type { PaymentHooks } from '../app-kit/index.js';
import { db } from '../init.js';

export const PAYMENT_HOOKS: PaymentHooks = {
  onResult: async (result) => {
    // result: { resultId, paymentId, accountId, reference, status, amountMinor, currency,
    //           provider, providerId, mode, late, resolvedBy? }
    if (result.mode === 'test') return; // test never counts as money
    await db.collection('SettledPayments').doc(result.resultId).create({ ... });
  },
  onAlert: async (alert) => {
    // alert: { type, accountId, provider, mode, detail, expiresOn?, daysLeft?, reference?, reasons? }
  },
};
  • Once. Each status reaches onResult once. If it throws, Arc tries again later with the same resultId, up to every hour, and raises delivery-failed after 10 tries. A crash just after your hook ran is the one way to hear something twice, so write with resultId as the document id, as above.
  • Late money. A payment that failed or that you ended can still become paid, as a buyer may already be paying. It arrives as a second result, paid with late: true. Decide what that means for your app. Connect's page cannot be closed early, so this will happen.
  • Test. mode is on every result. Check it before counting money.

Your hooks are not loaded by the webhook, so what they import cannot slow it down.

Alerts

typeWhen
key-expiringAt 30, 7 and 1 days before the day the merchant typed for the key's end, and when it has come. Worldline's API keys end; no call says when, so ask for the date.
key-refusedThe provider refused the keys, in use or in the daily check. Goes away by itself when they work again.
webhook-silent3 payments in a row finished with no event, whether the sweep or your own readPayment found them. Neither provider's docs show a call that says a webhook was switched off, so this is how Arc notices: it was never added, or it is off. Goes away when an event arrives.
payment-heldA payment is held for a person (below).
delivery-failedYour onResult has failed 10 times for one payment.

Each is said once until it changes. onAlert is the only way a held payment is told, so fill it in. What is wrong now is also in the account's problems, so your screens can show it.

Read, end, refund

CallWhat it does
readPayment({ accountId, reference })Reads the provider now, applies what it says and answers the payment: { status, amountMinor, currency, mode, late, heldReasons, refundedMinor, closesAtIso, providerStatus, method, eventSeen, checked }. Use it while a buyer waits. If the provider cannot answer, checked is false and you get what Arc last knew.
endPayment({ accountId, reference })Reads first, as the money may have come, then ends the page and marks it cancelled. The sweep goes on reading until the page's life is over, looking for a payment made on it even when the page itself can no longer be read. Payrexx offers no such look: once a gateway is deleted, only an event can name its transaction.
refundPayment({ accountId, reference, amountMinor?, by })Whole (what is left) or in part, through the provider, never more than was paid. If the provider gives no answer, the amount stays set aside and further refunds answer busy, because it may have gone through: look in the provider's own account, then call settleRefund.
settleRefund({ accountId, reference, went, by })A person says whether a refund left with no answer went through. refundingMinor in readPayment shows one is waiting.
resolveHeldPayment({ accountId, reference, as, by })A person decides a held payment: paid, failed or cancelled. Your onResult hears it, with resolvedBy.

A payment held for a person

Arc never says paid when something does not add up. heldReasons says why:

  • amount, currency, reference: the provider says paid, but not this.
  • mode: the provider says the payment was on its other system.
  • provider-status: an open payment is now refunded or charged back, or a payment still unfinished 3 days after its page closed.
  • provider-unread: the provider has not answered for 3 days after the page closed.
  • disconnected: the account's keys are gone while its page could still be paid, so nothing can read it now.

How it works

  1. merchantPaymentWebhook takes a delivery at the account's address. Where the provider signs, it checks the signature over the exact bytes, with a key the server holds, before reading the body. It finds the payment, writes the event's id once, and answers.
  2. onMerchantPaymentEvent reads the payment back from the provider. Only that answer can say what happened. Amount, currency, reference and system are compared with your record.
  3. sweepMerchantPayments, every 2 minutes, reads what is still unfinished (further apart each time, up to 15 minutes) and retries results your app has not taken. A lost webhook recovers with no browser. A page nobody paid on is cancelled once it closes. A payment under way is never closed as unpaid: it is read on for 3 days, then held for a person. A cancelled or failed payment goes on being read until its page has closed.
  4. checkMerchantAccounts, daily, warns of keys ending, tries each account's keys, and clears event records older than 7 days.

The rules that always hold

Each has tests in functions/src/__tests__/merchantPayments.spec.ts, under its number, or in the two specs beside it.

RuleHow
1No browser ever holds a key.Keys live in MerchantAccountKeys, closed to every browser, admins included. They come back in no answer. startPayment reads no key from its input.
2No secret in an address, and no account named by the sender alone.The address holds a random public id, which proves nothing. An event signed with a key the server does not hold is refused with 401, and nothing is written. Payrexx's unsigned events only prompt a read back; an id they name counts only if that transaction is this gateway's.
3The signature is checked over the exact bytes received, before anything is read.From rawBody, never a body put back together. With no raw bytes it answers 400.
4An event is never enough to say paid.Only a read back can, and any difference is held.
5Paid means the money is secured.A strict table per connector (below). An unknown status is never paid.
6No fallback, ever.Each connector's address follows the mode alone, and no account value can name a host. Keys of one mode never serve the other. A missing or half-set account is refused with a plain reason. The pretend provider cannot be live.
7Once, in any order.Duplicates are dropped by event id (for Payrexx, which gives none, by a hash of the bytes). Paid and held never change by themselves. Unsigned events prompt at most one read in 30 seconds, so a flood of them cannot become a flood of calls on the merchant's account.
8Answer inside 10 seconds, cold start included.The webhook records and answers. A test holds what it loads: no SDK, none of your code. A slow database gets a 503 within 6 seconds of the code starting, and the provider sends it again. Only a real cold start can be measured (Prove a connector); if it is too slow on your project, keep the function warm with ARC_KEEP_WARM=merchantPaymentWebhook (Keep a function running).
9Nothing secret or personal in a log.Logs carry a type and a provider's name. No raw event is kept, and an event's record is gone after 7 days. A provider's or a library's error words are filtered or dropped.
10A key can expire: tell the app first.Alerts.
11The payment page's address is checked.https, the provider's own domain, no credentials or port, and a live page never on pre-production. Anything else is refused, and the page ended.

Build and test with the pretend provider

A provider with no network, for your unit tests, the emulator and a dev project. It signs its events and is read back like a real one, so your flow runs through every rule. It is test mode only, and offered only on the emulator, in tests, or where you set ARC_PAYMENTS_PRETEND=on in functions/.env.YOUR_PROJECT. Never set that on a live project.

import { capturePaymentHooks, connectPaymentAccount, pretendPayment, startPayment } from '../app-kit/index.js';

const results = [];
const hooks = capturePaymentHooks({ onResult: (r) => results.push(r) });

await connectPaymentAccount({ accountId: 'b1', provider: 'pretend', mode: 'test', by: 'me', fields: {
  accountName: 'My shop', secretKey: 'any-8-chars', webhookKeyId: 'key1', webhookSecret: 'any-8-chars',
} });
await startPayment({ accountId: 'b1', amountMinor: 1250, currency: 'CHF', reference: 'order-1', returnUrl: 'https://a.example/' });
await pretendPayment({ accountId: 'b1', reference: 'order-1', outcome: 'paid', processNow: true });
// results[0].status === 'paid'
hooks.stop();
In pretendPaymentWhat it gives you
outcomepaid, failed, cancelled, waiting, waiting-approval, authorized, charged-back, wrong-amount, wrong-currency, wrong-reference
delivernow (one event, the default), twice (a duplicate), none (a lost webhook, for the sweep or readPayment to find)

For a late payment, call endPayment and then pretendPayment with paid. A secret key of refuse-this-key makes the provider refuse the keys. Its page address (pretend-pay.arccms.invalid) goes nowhere, so a dev screen shows its own stand-in and calls pretendPayment from a dev function.

Prove a connector

A connector's proven is set in code, for each provider, once this has passed on the provider's own account. Until then, no merchant can pick it. Keys are yours to type: npm run payments:proof takes them at a prompt that shows nothing, and goes through the same calls your app makes. Do not put them in chat, a file or a command line.

  1. Build the functions with the feature on, and deploy the four functions above to a project you can test on. Leave the change to src/custom/features.ts uncommitted in Arc CMS itself:

    npm run build --prefix functions

  2. Run it. --project=<id> chooses the project, as in Run scripts and keep data:

    npm run payments:proof -- --provider=worldline-connect --mode=test
    npm run payments:proof -- --provider=payrexx --mode=live
  3. It connects, then tries a wrong key and a forged event by itself. The forged event goes first so its time can be a cold start, before the provider's own address check wakes the function. Then it shows the webhook address for you to add, and a list of checks to run, as many times as you like:
    • Pay. Follows what the provider says, with the seconds since the page opened, waits up to 2 minutes for the provider's event, and offers a part and a whole refund. Once for each way of paying.
    • End a page nobody has paid, and write down what a buyer now sees.
    • Late money. You stop just before the last button, it ends the page, you press the button. Money the provider takes must arrive as paid with late.
    • The sweep. You remove the webhook address and pay. Nothing reads the provider from your machine, so only the deployed sweep can find it, 2 to 15 minutes apart.
  4. It lists each check as as the rules ask, not as the rules ask or for you to judge, and what this run did not try, then removes the keys. It never sets proven: you do, in the connector.

A payment on a live account moves real money. If you stop with Ctrl+C the keys stay stored. To take them out, run it again with --remove and no keys to type:

npm run payments:proof -- --provider=payrexx --mode=live --remove

Where a provider signs nothing, the forged event runs on a page kept for it and ended afterwards, so it never counts as an event on a payment you make. A row saying event arrived is the provider's own.

What must be seen, for each provider and each way of paying (card, TWINT), before its proven is set. Only the part capture is done by hand, in the provider's own admin:

  • Which status means the money is secured, and whether it comes while a buyer waits. If a Connect card stays at CAPTURE_REQUESTED until the day's end, the table above would keep a buyer waiting at the counter: decide, and write it here.
  • A wrong key is refused; a forged event answers 401 (Connect) or changes nothing (Payrexx).
  • The webhook answers inside 10 seconds from cold, and Connect's address check passes.
  • A paid event reaches the record; with the webhook removed, the sweep still finds it.
  • Ending a page works, and what a buyer sees after it. Paying just before it: late.
  • A part refund and a whole refund. A part capture reads as its real amount, so it is held.
  • Connect: TWINT and wallets go straight to a sale, with requiresApproval: false sent for them as well as for cards.

On Connect: the live API address; whether it insists on a buyer's email; the page's real host and subdomain; that an event carries merchantReference, or it is dropped and left to the sweep; the time an API key lasts. On Payrexx: whether it has a test system; the webhook's real shape, as its docs' webhook pages could not be read; that a gateway's answer names its transactions, or a sweep alone can never say paid, and that a transaction carries invoice.paymentRequestId, or an id from an event is never believed; that a transaction on version 1.0 of its API carries mode, or every paid one is held; whether /Transaction/?limit=1 tells a good key from a bad one; whether the page can be on a domain of the merchant's own, which would be refused today.

To try an unproven connector from your own screens on a project, set ARC_PAYMENTS_TRY in functions/.env.YOUR_PROJECT: worldline-connect for test mode, worldline-connect:live or payrexx:live for live, several with commas. Never set it on a project merchants use.

Add a provider

This is for Arc CMS itself. A provider is one file in functions/src/merchant-payments/connectors/ implementing PaymentConnector from types.ts, and one line in connectors/index.ts. No app changes. A provider whose page takes a form posted from a browser, as myPOS does, needs ConnectorStarted to carry the form and a page of Arc's own to send the buyer there. Load any SDK with await import(), so the webhook never pays for it.
