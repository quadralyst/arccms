Send email from your app

Your own Cloud Functions can send transactional email, such as a receipt, a report or a reminder, with sendAppEmail from the app kit. It sends one of your templates in the language you ask for, or a subject and body you built, inside the site's email layout, to the addresses you hold, with files attached. It goes through the same engine as Arc CMS's own email: the switches in Settings, Email, suppression of bounced addresses, retries, and a log for each address in Email Logs. When each email is sent, fails or bounces, an AppEvents entry with your reference tells your app, so it can show "Sent" or "Not delivered" on its own screen.

Marketing email stays with lists and consent (Email): sendAppEmail sends transactional email only.

An example: a shop's daily closing

When a shop's last till closes, the app emails the day's closing to the addresses the owner set, in the business's language, with two CSV files. First the template, in functions/src/custom/email-templates.ts:

import type { AccountEmailLanguages, AppEmailTemplate } from '../app-kit/index.js';

export const APP_EMAIL_TEMPLATES: AppEmailTemplate[] = [
  {
    key: 'daily_closing',
    title: 'Daily closing',
    languages: {
      en: {
        subject: 'Closing for ##SHOP## on ##DATE##',
        body: '<h1>Closing for ##DATE##</h1><p>Takings: ##TOTAL##</p>##FIGURES##<p>The sales and payments are attached.</p>',
      },
      de: {
        subject: 'Tagesabschluss ##SHOP## vom ##DATE##',
        body: '<h1>Abschluss vom ##DATE##</h1><p>Umsatz: ##TOTAL##</p>##FIGURES##<p>Verkäufe und Zahlungen sind angehängt.</p>',
      },
    },
    sample: { SHOP: 'Corner Café', DATE: '20 October 2026', TOTAL: '812.40' },
  },
];

export const ACCOUNT_EMAIL_LANGUAGES: AccountEmailLanguages = {};

Then the function that sends it, in a file of your own such as functions/src/custom/closing.ts, exported from functions/src/custom/index.ts:

import { onDocumentUpdated } from 'firebase-functions/v2/firestore';
import { arcDocument } from '../arc-config.js';
import { escapeEmailHtml, sendAppEmail } from '../app-kit/index.js';

export const onClosingDone = onDocumentUpdated(arcDocument('businesses/{bid}/closings/{cid}'), async (event) => {
  const closing = event.data?.after.data();
  if (!closing || closing['status'] !== 'done' || event.data?.before.data()?.['status'] === 'done') return;
  const { bid, cid } = event.params;

  const rows = closing['lines'].map((l: { name: string; amount: string }) =>
    `<tr><td>${escapeEmailHtml(l.name)}</td><td>${escapeEmailHtml(l.amount)}</td></tr>`).join('');

  await sendAppEmail({
    to: closing['reportTo'],                      // the addresses the owner set
    template: 'daily_closing',
    language: closing['language'],                // such as 'de'
    data: {
      SHOP: closing['shopName'],
      DATE: closing['dateText'],
      TOTAL: closing['totalText'],
      FIGURES: { html: `<table>${rows}</table>` },
    },
    attachments: [
      { name: 'sales.csv', contentType: 'text/csv', content: closing['salesCsv'] },
      { name: 'payments.csv', contentType: 'text/csv', content: closing['paymentsCsv'] },
    ],
    replyTo: closing['ownerEmail'],
    dedupeKey: `closing-${cid}`,                  // a retried trigger sends nothing new
    ref: `businesses/${bid}/closings/${cid}`,     // comes back with the outcome
  });
});

The till learns whether it went from AppEvents (The outcome back to your app).

Write your templates

Each entry of APP_EMAIL_TEMPLATES has:

FieldWhat it is
keyIts name in your code, a-z, 0-9 and _, such as daily_closing. The admin's list shows it as app.daily_closing.
titleIts name in the admin's template list.
languagesOne version per language, by code (en, de, pt-br): a subject, a body (the inside of the email, HTML) and, if you like, a previewText (the line a mail app shows after the subject).
sampleTag data for the admin's preview, such as { DATE: '20 October 2026' }.

Write the body only: Arc CMS wraps it in the site's email layout, with the logo, colours and font from Email, Brand Kit, and a footer with the company name and address. ##TAG## tokens are filled from the data you send; a tag is capitals and _ only, and its data key is the same (DATE fills ##DATE##). Text is shown as text, so a name with < in it cannot break the email. For HTML you build, such as a table of figures, pass { html: '...' }: it goes in as written, so escape what you put inside it with escapeEmailHtml. The site's own tags work too, such as ##COMPANY_NAME## (see Email tags).

A mistake in the file (a key used twice, a language with no subject or body) stops the functions from loading, so the deploy fails with a message naming the file and what to change. The admin cannot edit your templates: they are your code, changed in this file and live with the next functions deploy.

What sendAppEmail takes

import { sendAppEmail } from '../app-kit/index.js';
FieldWhat it is
toOne address or a list, up to 50. Each address gets its own log, so suppression, bounces and status are per address.
template, dataThe key of one of your templates, and the data for its tags. Or, instead:
subject, html, textA subject and body you built (the body wrapped in the site's layout), and a plain-text version if you have one.
languageThe language to send in, such as de or de-CH. Leave it out for the site's default language.
attachmentsFiles: { name, contentType, content }, the content as text (sent as UTF-8), a Buffer, or base64 text with encoding: 'base64'. Up to 10 files and 5 MB in all.
replyToWhere replies go. Default: the reply-to address in Settings, Email.
dedupeKeyA key stable for this email, such as closing-c9: calling again with it sends nothing new. Use one in every trigger, since a trigger can run twice.
refYour own reference, such as businesses/b1/closings/c9, kept on the log and returned in the outcome events.

The sender is the name and address in Settings, Email. sendAppEmail throws, saying what to fix, when the input is wrong (no address, an unknown template, files over 5 MB); nothing is sent then. Otherwise it returns one entry per address:

{
  logs: [
    { to: 'owner@example.com', id: 'aB3...', status: 'pending' },
    { to: 'books@example.com', id: 'Xy9...', status: 'suppressed', skipReason: 'suppressed' },
  ],
  ids: ['aB3...', 'Xy9...'],
}

pending is on its way. skipped and suppressed were stopped at once, with the reason: email_disabled (email off, or no provider), feature_disabled (App emails off), contact_disabled (an admin switched the address off) or suppressed (the address bounced or complained). duplicate: true means the dedupeKey was sent before; the id is that email's.

Which language is sent

The version for the language you ask for (de-CH finds de), else the site's default language (Settings, Languages), else English, else the first language the template has. The log records the language sent.

Attachments

Files are kept in Storage beside the log, not in the log itself: each log has its own copy in email-logs/{logId}/, under the install's upload folder. A retry sends the same files again. They are deleted with the log when Email Logs are purged (Settings, Email, Auto-Purge Email Logs, or Purge Old Logs in Email Logs). Only admins can read them, in Email Logs, and no browser can write them. An email that was stopped lists its files but stores none.

The outcome back to your app

For each of your emails, Arc CMS writes one AppEvents entry when its fate is known:

TypeWhendata
email.sentThe provider took it. With the Simulated provider, simulated: true as well.logId, ref, to, template
email.failedStopped at once (the reasons above), or the provider refused it on every try.The same, and reason
email.bouncedThe provider reported a bounce (it needs the email webhook, see Email).The same, and reason

Each comes once per log, whatever retries or repeated webhooks happen. React with your own trigger, as for any app event (Write your own Cloud Functions):

export const onEmailOutcome = onDocumentCreated(arcDocument('AppEvents/{id}'), async (event) => {
  const e = event.data?.data();
  if (!e || !String(e['type']).startsWith('email.')) return;
  const { ref, logId, to, reason } = e['data'];
  if (!String(ref ?? '').startsWith('businesses/')) return;
  // One entry per address, so the till can show "Sent" or "Not delivered" beside each.
  await db.doc(String(ref)).set({ emails: { [logId]: { to, outcome: e['type'], reason: reason ?? null } } }, { merge: true });
});

A bounced or complaining address is suppressed: the next email to it, from your app or from Arc CMS, is stopped with suppressed. Subscribing again does not lift a bounce; erasing the contact in Audience, Contacts does.

The switch

Settings, Email, Features has App emails, on unless an admin switches it off. Off, every sendAppEmail writes a skipped log with feature_disabled and an email.failed event, and sends nothing. Turning email off as a whole (the switch at the top of Settings, Email) stops it too.

Arc CMS's account emails in your languages

The sign-up code and password reset code emails, and the code for adding an email to an account (which uses the sign-up template), go in the member's language: the sign-in page sends the language it shows (see Member languages). Arc CMS writes them in English, in Settings, where an admin edits them. Word them in your languages in ACCOUNT_EMAIL_LANGUAGES, in the same file:

export const ACCOUNT_EMAIL_LANGUAGES: AccountEmailLanguages = {
  signup_otp_email: {
    de: { subject: 'Ihr Bestätigungscode', body: '<p>Hallo ##NAME##,</p><p>Ihr Code: <strong>##OTP##</strong>. Er gilt 10 Minuten.</p>' },
  },
  password_reset_otp_email: {
    de: { subject: 'Ihr Code zum Zurücksetzen', body: '<p>Ihr Code: <strong>##OTP##</strong></p>' },
  },
};

A member gets your version for their language, else for the site's default language, else the English template from Settings. English is always the template in Settings, so the file takes no en here. Keep ##OTP## in every version: it is the code.

In the admin

  • Email, Composer lists your templates, marked App, with their languages. They open as a preview, in each language, filled with their sample data, and cannot be edited there. Opening the composer brings the list up to date with your file (the syncAppEmailTemplates function), and so does each send.
  • Email Logs shows each email as it was sent, its language, Reply-To and your reference, and lists its files with an Open link.
  • Settings, Automations does not offer your templates for rules: they need your data.

Test it

On a dev project, choose the Simulated provider in Settings, Email. Nothing is sent: each email is recorded in Email Logs as it would have gone, files included, so you can open it there and check the whole flow, events included, with no real provider.

In your unit tests, captureAppEmails from the app kit records what would be sent, without Firestore, Storage or a provider. sendAppEmail still checks its input as for real, so a mistake fails the test:

import { captureAppEmails } from '../../app-kit/index.js';

it('emails the closing in the shop\'s language with both files', async () => {
  const mail = captureAppEmails({ defaultLanguage: 'en' });   // the site's default language
  try {
    await sendClosing('b1', 'c9');
  } finally {
    mail.stop();
  }
  expect(mail.emails).toHaveLength(1);
  expect(mail.emails[0]).toMatchObject({ to: ['owner@example.com'], template: 'daily_closing', language: 'de', ref: 'businesses/b1/closings/c9' });
  expect(mail.emails[0].attachments.map((f) => f.name)).toEqual(['sales.csv', 'payments.csv']);
});

Each captured email has to, template, languageAsked and language (the one sent), subject, html (with its tags still to fill), text, data, attachments (with their bytes as content), replyTo, dedupeKey and ref.

Deploy

Deploy your function as usual (Deploy only what changed). A change to your templates is live once the functions that send them are deployed, since each send reads them from the code. The admin's list catches up with the next send; to see it at once, deploy syncAppEmailTemplates too, which the composer calls. A change to ACCOUNT_EMAIL_LANGUAGES is live once the code functions are deployed: requestSignupOtp, requestPasswordReset and requestEmailLinkOtp (Deploy only what changed has the targets).
