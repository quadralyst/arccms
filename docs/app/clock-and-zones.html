Clock and time zones

A device's clock can be minutes off, and the people using your app can be anywhere. Arc CMS gives your app one true "now", tells you when a device clock is wrong, and shows every moment in the right zone: the site's, each person's own, or the zone of a place your app owns.

Three kinds of zone

A zone is always an IANA name, such as Europe/Zurich or Asia/Kolkata, never an offset like +05:30 or an abbreviation like CET: only a name knows when summer time starts. Old spellings some browsers still report, such as Asia/Calcutta, become the current name.

ZoneWhat it isWhere it is setUsed for
Site zoneThe site's own, one for everyoneAdmin, Settings, Localization, Time zone. The setup wizard fills it from the browser of the person setting up the site. Stored as timeZone on Settings/localizationDates on published pages, so every visitor sees the same day. UTC until an admin sets one
Member zoneEach person's own, in the admin area tooFollows the device. A person can choose another on the profile page (Time zone), kept on that device like the member languageEvery time on the admin and member screens: "Draft saved", created dates, feedback, transactions
Place zoneThe zone of something your app owns, such as a shop or an officeYour app stores it on its own records, for example with <arc-zone-picker>A time that belongs to the place: "22:00 Zurich (01:30 for you)"

When a zone is missing or unknown, a place falls back to the site zone, then UTC; a member falls back to the device, then UTC.

Show a time

Use the arcTime pipe (src/app/core/time/arc-time.pipe.ts) in place of Angular's | date, which takes a zone only as a fixed offset and so is wrong on one side of every summer time change:

import { ArcTimePipe } from '../../app/core/time/arc-time.pipe';

{{ order.createdAt | arcTime }}                          <!-- 24 Oct 2026, 22:00, the reader's zone -->
{{ order.createdAt | arcTime: 'time' }}                  <!-- 22:00 -->
{{ order.createdAt | arcTime: 'ago' }}                   <!-- 2 minutes ago -->
{{ order.createdAt | arcTime: 'dateTime' : 'site' }}     <!-- in the site's zone -->
{{ meeting.at | arcTime: 'place' : office.zone }}        <!-- 22:00 Zurich (01:30 for you) -->

The arguments are the format, the zone and, rarely, a locale. The moment can be a Date, epoch milliseconds, an ISO string or a Firestore Timestamp; an empty one shows nothing, never "Invalid Date". A core test fails if a core screen uses | date, so the same is worth doing in your own screens.

The zone argument is 'member' (the default), 'site', 'device', an IANA name, or a place with a name for the label: { zone: shop.zone, name: shop.name }. 12 or 24 hours, and the words "Today" and "2 minutes ago", follow the language on screen at once, with no reload; for English, the browser's regional English decides (en-GB writes 22:00).

In code, call arcTime(value, format, zone) from src/app/core/time/arc-time.service.ts, or format() on the ArcTime service there. For a table, app-global-table's date columns take dateZone: a zone, or a function of the row for a table of several places (see its README.md).

Example: a chat between Zurich and Pune

Anna is in Zurich and Ravi in Pune. Arc CMS has no chat; this shows how the pieces fit.

  • A message is one moment, stamped by the server, so a phone set ten minutes fast cannot reorder the conversation: addDoc(messages, { text, author, sentAt: serverTimestamp() }). To show a message before the server has stamped it, read it with snapshot.data({ serverTimestamps: 'estimate' }).
  • Each sees their own time: {{ m.sentAt | arcTime: 'time' }} shows a message sent at 20:00 UTC as 22:00 to Anna and 01:30 to Ravi.
  • Day breaks follow each reader: {{ m.sentAt | arcTime: 'day' }} is "Today" for Anna, and already "Today" (Sunday) for Ravi, whose Saturday messages are now "Yesterday".
  • "2 minutes ago" uses the true now: {{ m.sentAt | arcTime: 'ago' }} is counted from ArcClock, so a phone that is slow does not say "in 8 minutes".
  • A time that belongs to a place shows both: a call at the Zurich office, {{ call.at | arcTime: 'place' : { zone: 'Europe/Zurich', name: 'Zurich office' } }}, reads "22:00 Zurich office (Sun 01:30 for you)" to Ravi and "22:00" to Anna.

The clock

ArcClock (src/app/core/time/arc-clock.ts) measures how far the device clock is from the server and corrects it. Inject it where you need the true time:

MemberWhat it is
now()A signal: the corrected time in epoch milliseconds, moving on every second. For templates and effects
exact()The corrected time at this instant, in place of Date.now()
offset()Server time minus device time, in milliseconds: positive when the device is behind. Under a second counts as 0, the measurement's own error
skewed()True when the device is off by more than the threshold (2 minutes unless you set another)
synced()True once a measurement has succeeded since the page opened
lastSyncedAt()When the last good measurement was, kept from an earlier visit too; null if never
sync()Measure now. Resolves true when it worked

It measures when it is first used, when the browser comes back online, when the page is shown again (at most once a minute) and every 30 minutes. A page that never uses it never measures.

How it measures

The server's time is the Date header of a tiny file on your own Hosting, /_arc/clock.json: no Firestore read, no function, nothing to pay, and it works on the sign-in screen. It is right to about half a second plus half the round trip, plenty for a warning and for showing minutes. Order between records comes from serverTimestamp(), never from this clock.

An old Date header from a cache would be wrong, so the answer always comes from the network: each request has a new address, asks for no cache, and firebase.json sends Cache-Control: no-store for /_arc/. The installable app's service worker has no rule for /_arc/ (a test fails if one is added), and an answer that still looks cached (an Age header above 0, no Date, or a round trip over 5 seconds) is ignored. Keep /_arc/ out of your own caching too.

Offline

The last offset is kept on the device, so a page opened offline still shows the corrected time; synced() stays false until a measurement succeeds. A device clock changed while offline is not noticed until the next measurement. On npm run dev the dev server on your own machine answers, so the offset is about 0.

When a clock counts as wrong

Two minutes by default. Set your own in src/custom/clock.ts:

import type { CustomClock } from '../app/core/time/clock-config';

export const CUSTOM_CLOCK: CustomClock = {
    skewSeconds: 30,
};

A value that is not a number of seconds above 0 stops npm run dev and npm run build with a message saying what to write.

Stamping records

Let the server stamp what you store: serverTimestamp() in Firestore, and request.time in your rules. When a record has to be stamped on the device, for example one written while offline, use ArcClock.exact() instead of Date.now(): it is the device's time corrected by the last measurement. A rule that compares such a time with request.time should allow a few minutes either way, and skewed() tells you when to warn the person before it fails.

The site zone and published pages

The publish functions write dates into your pages, the cards of a list and a page's published and updated dates, in the site zone (functions/src/shared/time-zone.ts), and the browser shows the same when it renders a page itself. An article published at 00:30 in Zurich shows that day. A site set up before the time zone existed uses UTC until an admin sets one: Settings, Localization says so and offers the admin's own zone in one click. Pages published before the change keep their dates until they are published again.

Testing a wrong clock

  • By hand, on a deployed site: set the device's clock a few minutes ahead, open the app, and <arc-clock> shows the warning; set it back and show the page again, and the warning goes.
  • In a spec, give ArcClock its own network and clocks with the ARC_CLOCK_SOURCES token (fetch, deviceNow, monotonicNow), and its threshold with ARC_CLOCK_SKEW_MS; or provide a stand-in ArcClock with a now signal. A stand-in ArcZones with member, site and device fixes the zones.

What stays as it was

  • Emails and SMS: the server does not know a person's zone, which is kept on their device.
  • Scheduled Cloud Functions keep their UTC schedules.
  • Admin screens that show only a date, such as the tags and waitlist lists, still show the device's day.
