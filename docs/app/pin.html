PINs for your app

A 6-digit PIN lets people sign in on a shared device without an email or a phone: staff at a till, a family tablet. Your own function checks it with Arc CMS's PIN code, the same hashing, rules and lockout phone sign-in uses, and hands back a sign-in token.

A PIN store

import { createPinStore } from '../app-kit/index.js';

const pins = createPinStore('till', { maxAttempts: 5 });

The namespace keeps kinds of PIN apart: a person can have a till PIN and a staff PIN, each with its own lock. It is lower case letters, digits, - and _, 2 to 31 characters, starting with a letter. maxAttempts is 1 to 20, default 5.

CallDoes
pins.set(uid, pin)Sets or replaces the PIN, which also unlocks it. Refuses one that is not exactly 6 digits, or too easy to guess (111111, 123456, common patterns), with a message the person can act on.
pins.check(uid, pin){ ok: true }, or { ok: false, reason } with none (no PIN), locked, or wrong and remaining tries. A wrong PIN counts; the last allowed one locks it. A correct PIN resets the count.
pins.has(uid)Whether the person has a PIN here.
pins.clearLock(uid)Unlocks without changing the PIN, for example when a manager vouches for the person.
pins.remove(uid)Removes the PIN.

The uid is the person's Firebase Auth uid, such as the one createAppAccount() returns (see App accounts).

Where PINs are kept

In app_pins/<namespace>__<uid>, which Arc CMS's rules close to every browser. Only your functions reach it, through the store. A PIN is never stored: only a salted, peppered hash, as for phone sign-in. It is a separate collection from phone sign-in's auth_pins, so your PIN and a person's phone PIN never touch. When an account is deleted, its PINs in every namespace go with it.

There is no timed unlock and no reset by code: unlocking is your app's decision, with clearLock() or a new set(). Arc CMS's reset by SMS code is for phone sign-in's PINs only.

Rate limits

Lockout protects one person's PIN. A rate limit protects your function from someone trying many people. Count each attempt against a key with consumeRateLimit(key, max, windowMs, message); it refuses with resource-exhausted and your message once max is reached in the window.

KeyFor
hashedKey('till-device', deviceId)Something your app knows, such as the device. The value is hashed, so no raw id is stored, and the scope keeps it apart from Arc CMS's own keys.
callerKey(request)The caller's address, hashed. It takes the address Google's front end saw, right for a callable the browser calls directly. Behind a Firebase Hosting rewrite, the last address is Hosting's: pass { trustedProxies: 1 }, or count by a key of your own instead.

Use both: a per-device or per-address limit stops one place from trying many people, and the per-PIN lockout stops anyone from trying many PINs on one person.

Sign in with a PIN: a complete callable

// functions/src/custom/pinSignIn.ts
import { onCall, HttpsError } from 'firebase-functions/v2/https';
import { consumeRateLimit, createPinStore, hashedKey, issueSignInToken } from '../app-kit/index.js';

const pins = createPinStore('till');
const MINUTE = 60 * 1000;

/** Staff sign in at a till: { uid, pin, deviceId } in, a sign-in token out. */
export const signInWithAppPin = onCall(async (request) => {
  const uid = String(request.data?.uid ?? '');
  const deviceId = String(request.data?.deviceId ?? '');
  const tooMany = 'Too many tries. Wait a few minutes.';
  await consumeRateLimit(hashedKey('till-device', deviceId), 30, 10 * MINUTE, tooMany);
  await consumeRateLimit(hashedKey('till-staff', uid), 10, 10 * MINUTE, tooMany);

  const result = await pins.check(uid, request.data?.pin);
  if (result.ok) return { token: await issueSignInToken(uid) };
  if (result.reason === 'locked') throw new HttpsError('permission-denied', 'This PIN is locked. Ask a manager.');
  if (result.reason === 'none') throw new HttpsError('failed-precondition', 'No PIN is set for you yet.');
  throw new HttpsError('permission-denied', `Wrong PIN. ${result.remaining} left.`);
});

/** A manager sets or resets a member of staff's PIN. */
export const setStaffPin = onCall(async (request) => {
  // ... check that the caller may do this, for example with isArcAdmin(request.auth?.token) ...
  await pins.set(String(request.data?.uid ?? ''), String(request.data?.pin ?? ''));
  return { ok: true };
});

Add signInWithAppPin and setStaffPin to functions/src/custom/public-callables.txt, deploy them (see Write your own Cloud Functions), and in the browser exchange the token:

import { signInWithCustomToken } from '@angular/fire/auth';

const { token } = (await arcCallable<{ uid: string; pin: string; deviceId: string }, { token: string }>(
  this.functions, 'custom-signInWithAppPin')({ uid, pin, deviceId })).data;
await signInWithCustomToken(this.auth, token);

Say the same thing for a wrong uid as for a wrong PIN if your screen lets people type their own id: otherwise the answer tells a stranger which ids exist. On a till where staff pick their name from a list, that is already known and the plain messages above are fine.
