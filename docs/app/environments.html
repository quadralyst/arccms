Dev, staging and production

An app usually needs several Firebase projects: one to develop on, one to test a release on, one for real users. Each has its own web settings, and every build, deploy and script picks the project the same way: by its .firebaserc alias or its id.

How a build knows its project

A build gets the Firebase project it talks to from ARC_PROJECT. npm run deploy sets it to the project it is deploying to, so a deploy always builds the site for that project, and a site can never go out talking to another one. For that project, the build uses:

  1. src/environments/firebase-web.<projectId>.ts, the project's own web settings, when you have fetched them (below);
  2. otherwise the environment file you edited by hand: environment.prod.ts for the production alias, environment.ts for any other, only if it names that very project. If it names another, the build stops and prints the command that fixes it.

With no ARC_PROJECT, nothing changes: npm run dev uses environment.ts, and npm run build uses environment.prod.ts (or environment.ts with USE_DEV_ENV=true). An install with two projects keeps working as it is.

Add a project

  1. Give it an alias in the Firebase CLI:

    firebase use --add

    Choose the project and call it, for example, staging. This writes .firebaserc, which git ignores.

  2. Fetch its web settings:

    npm run arc:configure -- --project=staging --web-config=fetch

    The Firebase CLI reads the project's web app settings. They are stored in arccms.config.json under projects.<id>.firebaseConfig and written to src/environments/firebase-web.<id>.ts, which you commit. If the project has several web apps, the one an environment file already names is used; otherwise the command lists them and asks for --web-app=<appId>. Without the CLI, save the settings the Firebase console shows (Project settings, Your apps) to a file and pass --web-config=<file>; JSON and the console's snippet both work.

  3. Set it up like any project, with the other arc:configure flags if it needs its own database, bucket or site (see Configure a project).

  4. Deploy it:

    npm run deploy -- --project=staging

    This builds the website with staging's settings and the functions, then deploys. The guided npm run deploy offers every alias. Then publish its static pages:

    npm run seed -- staging

The web settings are public: they tell the browser which project to talk to and grant nothing, so committing them is safe. What a visitor may read or write is decided by your security rules.

Build without deploying

npm run build:project -- --project=staging

The same as ARC_PROJECT=staging npm run build, on every operating system. The build prints the project and the file it used. ARC_PROJECT works with npm run dev too, to run the app against another project on your machine.

Guard production

Mark any project as production, whatever its alias is called:

npm run arc:configure -- --project=live --production=yes

The guided deploy then asks you to type the project id back before it deploys there, and admin scripts print (production) next to the project. The production alias and ids that say prod or live are guarded as before.

npm run deploy:dev and npm run deploy:prod never ask. They are for the default and production aliases only; use npm run deploy -- --project=<alias> for every other project.

Troubleshooting

You seeWhy, and what to do
"No web settings for <project>: ... is for <another>"The project has no web settings of its own and its environment file is for another project. Run the command the message prints.
"<project> has N web apps. Choose one with --web-app"Pick the app your site uses from the list and run the command again with --web-app=<appId>.
"The Firebase CLI did not answer"Install the Firebase CLI and sign in with firebase login, or use --web-config=<file>.
"firebaseConfig is for X, not Y"The settings you gave belong to another project. Fetch them for the right one.
