Version and build number

When someone reports a problem, the first question is which build they are on. Give your app a version, and every build says so: v1.2.0.25 android is version 1.2.0, build 25, built for Android. It shows under Logout in the admin's side panel, at the foot of the feedback panel, and it is saved with every feedback report, so nobody has to read it out.

Set the version

The version lives in custom/package.json, in the app's own folder at the root (Run scripts and keep data). Arc CMS never ships this file, so an app that has none has no version anywhere, and nothing is counted. Create it, or add the fields to the one you have:

{
  "name": "acme-tools",
  "private": true,
  "version": "1.2.0",
  "build": 24,
  "buildLabel": "web"
}
FieldWhat it is
versionYours to set, when you cut a release: three whole numbers, such as 1.2.0, with a suffix npm allows if you want one (1.2.0-beta.1). Anything else stops npm run dev and npm run build with a message.
buildThe last build number. npm run build counts it for you (below); you only touch it to start again.
buildLabelOptional: any text that says what the build is for, such as web, android or iOS beta, up to 40 characters. --label replaces it for one build.

How builds are counted

Every npm run build, and so every deploy of the website, takes the next number: one more than build. Once the build has succeeded, it writes the number back to custom/package.json and says so:

> Building v1.2.0.25 web
...
This is build v1.2.0.25 web. custom/package.json now says "build": 25: commit it with your next change.
  • A failed build leaves the file as it was, so its number is used by the next build.
  • No build, or 0: the next build is 1. To start again, set it to 0.
  • -1: the next build is 0, the lowest a build can be. A lower number counts as -1, with a warning.
  • Anything that is not a whole number, such as "24" or 2.5, stops the build before anything is built, instead of starting again from 1 and reusing numbers that already went out.
  • The dev server never counts: it shows the version with no number, v1.2.0 web. Restart it to see a new version.
  • One counter for every label: build 25 for Android and build 26 for iOS, so the number alone always names one build.

Commit the file

custom/package.json changes with every build, and it belongs in git: it survives a fresh clone and a new machine, and git log shows which change made each build. Commit it with your next change. Two branches that both build take the same number, and git shows a conflict on that one line when they meet: keep the higher number.

To be sure which code a build ran, each feedback report also carries the commit it was built from (below).

A deploy from CI counts in a checkout it throws away, so every run repeats the same number unless the job commits the file back. See Deploy from CI.

Skip the count, or label one build

OptionWhat it does
npm run build -- --no-bumpBuilds with no number (v1.2.0 web) and leaves custom/package.json alone: for a build you only want to try. ARC_NO_BUMP=1 does the same.
npm run build -- --label=androidThis build's label in place of buildLabel; --label= with nothing builds with no label. ARC_BUILD_LABEL=android does the same. Quote a label with spaces: --label="iOS beta".

Both work without the -- too (npm run build --no-bump), and npm run deploy and npm run build:project pass them on to the website build: npm run deploy -- --only hosting --no-bump.

Where it shows

  • Under Logout in the admin's side panel, small and muted, while the panel is open. A screen reader reads "Version v1.2.0.25 web". To turn it off there, set showVersion: false in src/custom/brand.ts (Brand the admin).
  • At the foot of the feedback panel, so the person sees what they are reporting from (Feedback button).
  • Anywhere you like, from APP_VERSION:
import { APP_VERSION } from '../app/core/version/app-version';

// APP_VERSION.text      'v1.2.0.25 android', 'v1.2.0' with no number, '' with no version
// APP_VERSION.version   '1.2.0'
// APP_VERSION.build     25, or null
// APP_VERSION.label     'android'
// APP_VERSION.commit    '533b6d02', or '533b6d02+changes'

It is fixed when the site is built; nothing is read at run time.

In feedback reports

Each report saves version.text and version.commit, and the admin's Feedback page shows them beside the device: v1.2.0.25 android · 533b6d02. The commit is the git commit the build was made from, with +changes when other files had changes not yet committed (the build's own change to custom/package.json does not count). Only the people reading feedback see it. A build with no version sends neither.

The security rules refuse a report with a field they do not know. When you update to an Arc CMS that sends the version, deploy the rules before the website, or every report from the new website is refused until the rules catch up.

Android and iOS with Capacitor

Arc CMS knows nothing about Capacitor; your app's own scripts do. Put them in custom/package.json, beside the version, so each platform's build carries its label:

"scripts": {
  "build:android": "cd .. && npm run build -- --label=android && npx cap sync android",
  "build:ios": "cd .. && npm run build -- --label=ios && npx cap sync ios"
}

Run one from the root with npm --prefix custom run build:android, or from custom/. Each is a build of its own, so it takes its own number.

Google Play and the App Store keep build numbers of their own (versionCode on Android, the bundle version on iOS), and refuse an upload whose number is not higher than the last one. Ours can be reset, so do not copy it into a store build after a reset.

Mistakes stop the build

You seeWhyFix
custom/package.json: "version" must be three whole numbersThe version is not like 1.2.0.Write three numbers with dots.
custom/package.json: "build" must be a whole numberThe build is text, a fraction or something else.Set it to the last build number, or 0 to start again from 1.
--label has a control character or is 41 charactersA label with a line break or a tab, or longer than 40 characters.Use a shorter, plain label.
npm run build does not know ...An option the build does not take.Use --no-bump or --label=<text>.
