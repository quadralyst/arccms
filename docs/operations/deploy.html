Deploy

One command deploys Arc CMS to a Firebase project: it asks which project and what to deploy, builds what is needed, and checks the result. Scripts and CI pass the same choices as flags.

Deploying a new project for the first time is covered in Deploy for the first time. To send just one function or just the rules, see Deploy only what changed.

Deploy with the guided deploy

Run it in a terminal and answer the questions. Each has a default in brackets; press Enter to take it.

npm run deploy

  1. Which Firebase project? The aliases in .firebaserc, plus the project chosen with firebase use. The default is the project you deployed to last from this checkout. "Another project id" takes any other.

  2. Its settings. The deploy prints the database, website, storage bucket, app users and functions region the project uses. They come from arccms.config.json, and the files generated from it are rebuilt on every deploy, so they are never stale. A project with no settings yet is offered a short setup, the same as npm run arc:configure (see Configure a project).

  3. What to deploy? See the table below. A choice whose files changed since its last deploy is marked "(changed since the last deploy)".

  4. Confirm. The summary shows the project, the Firebase config file and the exact command. For a production project (the alias production, or an id with prod, production or live as a part of it) you type the project id instead of pressing Enter.

The choices, remembered per project in .arc-deploy-state.json (not committed), are the defaults next time.

Deploy from a script or CI

With any option, npm run deploy skips the guided questions and passes the options on to firebase deploy. The one question it can still ask, in a terminal, is before it deletes functions (see Functions that are deleted). Off a terminal and with no options, it prints these examples and stops.

npm run deploy -- --only functions:arccms --project default
npm run deploy -- --only functions:arccms:arccms.<name> --project default
npm run deploy -- --only firestore --project default
npm run deploy -- --only storage --project default
npm run deploy -- --only hosting --project default

Copy these as they are, except for the project. arccms in functions:arccms is not a project or database name: it is the name of the Arc CMS functions codebase in firebase.json, the same in every install, and the arccms- in front of every function name. The part that differs from person to person is --project: an alias from your own .firebaserc (default, production) or a project id.

OptionWhat it does
--project <alias or id>The project. Without it: the firebase use project, else the default alias. The project is always passed to the Firebase CLI
--only <targets>What to deploy, as the Firebase CLI takes it. No --only deploys everything in the config
--yesLets a deploy of all the functions delete the ones the build no longer has without asking (needed off a terminal). Not passed on to Firebase itself; when there is something to delete, the deploy adds --force for it
--forceThe same as --yes, and passed on to Firebase
--probeAfter a deploy that included functions, checks that every callable can be reached from the browser (see Check the callables)
--non-interactiveA Firebase CLI option, passed on: the CLI asks nothing
--config <file>A Firebase config of your own. Otherwise the project's generated firebase.<projectId>.json is used when npm run arc:configure wrote one, else firebase.json

Either way, the deploy also:

  • builds the functions (npm run build --prefix functions) before any deploy that includes them;
  • waits 65 seconds and deploys again, up to two times, any function the Firebase CLI started but never reported as done (Google limits how many functions can change per minute);
  • fails when a function still never reported success, and prints the command that redeploys it;
  • stops with a plain message when you ask for hosting on a project with no website, or for storage rules on a bucket shared with another app;
  • records a whole deploy of a part (all functions, firestore, storage, hosting) for the guided deploy's "only what changed".

Plain firebase deploy skips all of this. It ships the functions exactly as they were last built, so new functions are silently missing, and it uses firebase.json, so a project set up with its own database, bucket or website gets the wrong ones. Always deploy through npm run deploy.

deploy:dev and deploy:prod

Two scripts deploy everything to the default or production alias in one go:

npm run deploy:dev
npm run deploy:prod

Each builds the website (deploy:dev with USE_DEV_ENV=true, so it uses the development environment), builds the functions, runs the deploy with --project <alias> --non-interactive --force and no --only, then publishes the static pages (npm run seed:dev or npm run seed:prod).

Both pass --force, so they delete the deployed functions the build no longer has without asking. Use the guided deploy when you are not sure what the build contains.

Regions

Every database read or write a function makes travels to the database and back. Functions far from their database are slow: with the database in Mumbai (asia-south1) and the functions in Iowa (us-central1, the Firebase default), one sign-in step takes several seconds. So the functions run next to the database, in the region set by functionsRegion (see Config keys).

Before every deploy that includes functions, the deploy compares the two. It looks up the database's location once per project and remembers it in .arc-deploy-state.json.

  • No Arc CMS function deployed yet: the deploy sets functionsRegion to the database's region, says so in one line, and deploys there. Commit arccms.config.json and src/environments/arc-install.ts afterwards. A deploy with options that also publishes the website stops first, because the website was built for the old region: build it again, then deploy.
  • Functions already deployed somewhere else: the deploy warns and deploys anyway. It never moves live functions. The guided deploy asks once whether to keep warning for that project.

A database in a multi-region location counts as next to the functions in one of its regions: nam5 with us-central1, eur3 with europe-west1. A location with no functions of its own gets the nearest region that has them.

The region reaches three places, all written by npm run arc:configure: the functions (ARC_FUNCTIONS_REGION), the website, which calls them there (arc-install.ts), and the Hosting rewrites to the unsubscribe and preference functions (firebase.<projectId>.json). To choose it yourself, before the first deploy:

npm run arc:configure -- --project=default --functions-region=asia-south1

Changing functionsRegion after the functions are deployed moves the whole install: a deploy creates every function in the new region, the website must be built and deployed again to call them there, and the old ones stay until a full functions deploy deletes them. Plan it as a release, not a setting.

A region costs a little more or less than another per call, but at the free allowance most sites stay inside, the difference is nothing, and functions next to the database also stop the paid traffic between regions.

Functions that are deleted

A deploy of all the functions (--only functions, --only functions:arccms, or no --only) makes the project match the build, so it deletes the Arc CMS functions the build no longer has: those of a feature turned off in src/custom/features.ts, a search collection removed from functions/src/custom/search-sources.ts, or a function that was renamed.

  • Before deploying, it lists them and asks once. The guided deploy asks on its own prompt.
  • Off a terminal it needs --yes (or --force). Without it, it stops and deploys nothing.
  • If the Firebase CLI skips a delete (it does when another function fails), the deploy deletes it afterwards.
  • A deploy of named functions (--only functions:arccms:arccms.<name>) never deletes anything.
  • Only the arccms codebase is compared, so another app's functions in the same project are never touched.
npm run deploy -- --only functions:arccms --project default --yes

A deleted function's URL stops working, for example a payment webhook registered with the payment provider or a link in an email already sent.

When the order matters

"Everything", deploy:dev and deploy:prod run one firebase deploy, and the Firebase CLI decides the order of the parts. That is fine for most changes. When a change tightens a security rule so that the browser must go through a new function, or stops the browser reading something older website code still reads, deploy in steps instead, so nothing is refused in between:

  1. The functions, so the new ones exist.

  2. The indexes (npm run deploy -- --only firestore:indexes --project <alias>). Indexes build in the background: wait until the Firebase console shows them enabled.

  3. The website, so no page still does what the new rules refuse.

  4. The rules, last (npm run deploy -- --only firestore:rules --project <alias>, and storage if they changed).

If the rules go out first, the refused reads and writes fail at once. To recover, deploy the previous rules again from git.

After the deploy

Check the callables

Firebase lets the browser call a callable function when it creates it. If that step is missed, for example in a partly failed deploy, every browser call to it fails with HTTP 403, and later deploys do not repair it. The guided deploy checks every callable it just created. With flags, add --probe, or run the check yourself after a deploy that adds a callable and before a release:

FIREBASE_PROJECT=YOUR_PROJECT_ID bash functions/scripts/check-callable-access.sh

It reads the callables from the functions build (plus the app's list in functions/src/custom/public-callables.txt), so build the functions first. Give function names after the script to check only those, without the arccms- prefix (custom-<name> for an app's own). Set FIREBASE_REGION when the functions are not in us-central1; the deploy passes the project's region itself.

ResultMeaningFix
reachableThe browser can call itNothing
BLOCKED by Cloud RunThe function exists but the public may not call itRun the gcloud run services add-iam-policy-binding command the script prints, or delete the function and deploy it again (a fresh create grants access)
NOT DEPLOYED (404)The build has it, the project does notRebuild the functions and deploy again

Publish the static pages

Published content is served as static files that Cloud Functions write to Hosting one page at a time. A website deploy uploads only the build, so after one, the pages are published again: the guided deploy and deploy:dev/deploy:prod do it for you. To do it by hand:

npm run seed:dev
npm run seed:prod

seed:dev publishes to the default alias, seed:prod to production. It republishes every published content page and list page, the privacy and cookie policy pages, robots.txt, llms.txt, the sitemap and the RSS feeds. It uses your Firebase CLI login (run firebase login first) and does nothing for a project with no website.
