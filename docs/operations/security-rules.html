Security rules

The security rules decide what a browser may read and write in Firestore and Storage. Cloud Functions use the Admin SDK and are not bound by them. This page shows how the rules are organized, the access model, and how to change a rule without opening a hole.

An app built on Arc CMS writes its own rules in its own files: see Set security rules and indexes. Roles and the claims the rules read are explained in Roles and claims.

Where the rules live

FileHoldsOwned by
firestore.rulesThe Firestore rules of Arc CMSCore
storage.rulesThe Storage rules of Arc CMSCore
firestore.indexes.jsonThe Firestore indexes of Arc CMSCore
firestore.app.rules, storage.app.rules, firestore.app.indexes.jsonAn app's own rules and indexes. Optional: core ships noneThe app
.arc-build/The combined files Firebase deploys. Generated, not committedscripts/arc-rules-build.mjs

Firebase takes one rules file per database and one per bucket, so scripts/arc-rules-build.mjs combines the core and app files into .arc-build/. It puts each app rules file where the core file has the line // @arc-app-rules, inside the same scope, so app rules can call the core helper functions. It merges the app's indexes into the core ones and removes duplicates; a field override that both files set differently stops the build.

firebase.json runs the combine step before every Firestore and Storage deploy. To run it by hand, for example to read the combined result:

npm run rules:build

Keep the // @arc-app-rules line in both core rules files, on a line of its own. Without it the combine step stops, and no rules can be deployed.

The access model

Every rule answers one question: who is asking? The answers come from the ID token.

WhoHow the rules know
Anyone, signed in or notNo check. Published pages and the browser app read published content without signing in
A signed-in personrequest.auth != null
The owner of a users recordThe arccms_uid claim equals the record id, or the record's uid field equals the Auth uid
Staff (an admin or an editor)The arccms_role claim is admin or editor
An adminThe arccms_role claim is admin
Only Cloud FunctionsEvery client is refused (allow read, write: if false)

The onUserRoleChange function copies the role field of a users record into the arccms_role claim, and only the Admin SDK may change that field (admins do it through the adminSetUserRole callable), so nobody can make themselves staff.

Users

  • Read: your own record, or any as an admin. A browser query on users must filter on uid == request.auth.uid, or the rules refuse the whole query.
  • Create: never from a browser. Every sign-up creates its record on the server, which checks the email, sets the site's default role and refuses when sign-ups are closed; Add User does too (adminCreateUser).
  • Update: your own record, but never role, uid, isActive, status, authOwner, by, selfService, email, phone, phoneVerified, the detach fields, the premium and credit fields (with premiumProductId and premiumPaymentId, which say what granted the access), adminPasswordAt, and emailVerified only to false. A locked app account (by: 'app' without selfService: true, see App accounts) also never changes its name, photo or emailVerified. Admins may update any record except its role, uid, isActive, status, phone, phoneVerified, by, authOwner and adminPasswordAt: those, and deleting a record, go through the callables adminSetUserRole, adminSetUserBlocked, adminDeleteUser and adminSetPhone, which never leave the site without an active admin and check a new number. by, authOwner and adminPasswordAt say whether the admins hold a sign-in's password, which raising an unverified email relies on. No record may hold a password.
  • Delete: never from a browser (adminDeleteUser, or deleteMyAccount for your own).
  • Delete: admins only.

Any folder named users, email-logs, ai-calls or ai-files in the first two levels of a path is never public. Reading a file by its path is open where the table says so, but listing a folder is not: admins may list any folder, editors any folder but those four, at the bucket root or under the upload folder (an editor cannot list arccms/users/ any more than users/). A page that needs a set of files keeps their paths in Firestore, as the media library does.

The helper functions

The top of firestore.rules defines these, and storage.rules the same names with the same meaning. App rules may call the five marked stable; keep their names and meaning when you change core.

FunctionTrue whenStable for apps
isSignedIn()Someone is signed inYes
ownsUserRecord(userDocId)The signed-in person's arccms_uid claim is that record id. No claim means noYes
isAdmin()The arccms_role claim is adminYes
isEditor()An admin, or the arccms_role claim is editor (content staff)Yes
signedInByApp()The session came from an app's own sign-in token (sign_in_provider is custom). Core rules do not use itYes
sessionClaim(name)A claim from the session's own sign-in token (arccms_session), or null. Core rules do not use itYes
isAuthenticated()The same as isSignedIn(), used by core
arcRole()Returns the arccms_role claim, or an empty string

Two more live with the users rules: isOwnUserDoc() (the record's uid field is the caller) and hasNoPassword(data). Storage adds isAvatarUpload(fileName) (a profile photo as the profile page names it: JPEG, PNG or WebP under 1 MB), isStaffFileType() (the types staff may upload outside the library's Files) and isLibraryFile(fileName).

Never check a plain role claim. An app sharing the sign-in accounts may give its own admins role: 'admin', and they are not Arc CMS admins. Use isAdmin() or isEditor(), which read arccms_role. A test in the default suite fails if a plain role check comes back.

Change a rule safely

  1. Edit firestore.rules or storage.rules in Arc CMS itself (an app edits its own *.app.rules file instead).

  2. Add a test to tests/rules/firestore.rules.spec.ts or tests/rules/storage.rules.spec.ts that shows the new rule allows what it should and refuses what it should not, for each kind of caller.

  3. Run the rules tests and the whole suite:

    npm run test:rules
    npm run test

  4. Deploy the code the rule depends on first, and the rules last (see When the order matters):

    npm run deploy -- --only firestore:rules --project default

Rules only ever add access: if any allow that matches a request is true, the request is allowed. A narrower rule with if false does not take away what a broader one grants. To close something, change the rule that grants it.

The rule for published content is one catch-all, match /{collection}/{docId}, that tests the collection name: Firestore has no prefix matching. Any collection named arc_... (and not ending in _drafts) or Tags_... is therefore public to read. Never give private data a name like that.

The rules tests

npm run test:rules combines the rules, starts the Firestore and Storage emulators with the Firebase CLI under a demo project, and runs every spec in tests/rules/ against the combined files with @firebase/rules-unit-testing. It needs the Firebase CLI and Java, which the emulators run on. The files run one at a time (vitest.rules.config.ts).

They are not part of npm run test, because that needs no emulator. The default suite has its own guard instead: functions/src/__tests__/securityRulesRoles.spec.ts reads the rules files and fails if a known hole comes back, such as a signed-in person writing their own role, content writable by any signed-in person, or a path writable by everyone signed in. More on the test setup is in Testing.
