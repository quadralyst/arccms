Testing

One command runs every test of the website, the Cloud Functions, the scripts and the docs. The security rules have a second command, because they need the Firebase emulators.

Run the tests

From the repository root:

npm run test

In a terminal, Vitest keeps watching and reruns the tests you touch; press q to stop. To run everything once and stop, for example in a script:

npx vitest run

The functions folder has no test script of its own: its specs run from the root with everything else.

Run one file or one test

npx vitest run functions/src/__tests__/adminCreateUser.spec.ts

A path that contains brackets or parentheses, such as a page in a (group) folder, needs quotes in the shell. To run only the tests whose name contains some words, add -t:

npx vitest run src/app/core/features -t "resolveFeatures"

What runs

vitest.config.ts sets up one run for everything:

SettingValue
Specssrc/**/*.spec.ts, functions/src/**/*.spec.ts, scripts/**/*.spec.ts, and an app's custom/**/*.spec.ts

Setup for every specsrc/test/setup.ts (Angular) and functions/src/__tests__/setup.ts (Cloud Functions)

The rules tests in tests/rules/ are left out of this run (see Rules tests).

Write a component spec

Component specs use Angular's TestBed with Vitest (vi.fn(), vi.mock()). src/test/setup.ts already starts the Angular test environment and gives every spec Transloco with the real English strings, so a rendered template shows the text a person sees. Code that builds a message with a key, outside a template, can be checked against the same English with english(key, params) from src/test/english.ts, which also stands in for a component's translate function on a mock.

The part to plan for is Firebase. Many services reach it indirectly, and a spec must mock whatever would:

Your component usesIt pulls inDo this
<arc-page-header> (every admin and member page)The notification bell, the admin search box and AuthStateSpread ...headerTestProviders() first in providers
AuthServiceDbService, which injects FirestoreProvide a mock with the methods the component calls
AuthState (the auth store)Firebase Auth and AuthServiceProvide a mock
A signal storeIts data service and Firestore.overrideProvider(TheStore, { useValue: mockStore }), with signals for its state

headerTestProviders() is in src/test/header-test-providers.ts. Put it first, so a provider your spec declares for the same token wins. A page spec, following src/app/pages/admin/(transactions)/transactions.page.spec.ts:

import { TestBed } from '@angular/core/testing';
import { signal } from '@angular/core';
import { provideRouter } from '@angular/router';
import { NoopAnimationsModule } from '@angular/platform-browser/animations';
import { describe, it, expect, vi, beforeEach } from 'vitest';
import TransactionsPageComponent from './transactions.page';
import { TransactionsStore } from './transactions.store';
import { headerTestProviders } from '../../../../test/header-test-providers';

describe('TransactionsPageComponent', () => {
    const mockStore = { items: signal([]), isLoading: signal(false), getAll: vi.fn() };

    beforeEach(async () => {
        await TestBed.configureTestingModule({
            imports: [TransactionsPageComponent, NoopAnimationsModule],
            providers: [...headerTestProviders(), provideRouter([])],
        })
            .overrideProvider(TransactionsStore, { useValue: mockStore })
            .compileComponents();
    });

    it('loads the transactions', () => {
        const fixture = TestBed.createComponent(TransactionsPageComponent);
        fixture.detectChanges();
        expect(mockStore.getAll).toHaveBeenCalled();
    });
});

A page that extends BaseComponent also needs an ActivatedRoute mock, as that spec shows. To render in another admin language, import translocoTestingModule({ lang: 'hi' }) from src/test/transloco-test-providers.ts.

Write a Cloud Function spec

Function specs live in functions/src/__tests__/ or beside the code. functions/src/__tests__/setup.ts mocks the Firebase Admin SDK for every spec. In your spec:

  1. Mock ../init, the module that hands out db and owner (the Admin SDK Auth), with fakes that record what the function writes. Build the fakes in vi.hoisted(), because vi.mock() runs before the imports.

  2. Mock the firebase-functions module the function registers with, so the export is the handler itself. For a callable, onCall: (...args) => args[args.length - 1].

  3. Import the function after the mocks and call it with a request ({ auth, data }) or an event.

vi.mock('../init', () => ({ db: m.db, owner: m.owner }));
vi.mock('firebase-functions/v2/https', () => ({
    onCall: (...args: any[]) => args[args.length - 1],
    HttpsError: class HttpsError extends Error { constructor(public code: string, msg: string) { super(msg); } },
}));

import { adminCreateUser } from '../users/adminCreateUser.js';

For a Firestore trigger, mock firebase-functions/v2/firestore so the trigger records its handler, and take the handler once, at the top of the file: vi.mocked(onDocumentDeleted).mock.calls.at(-1)?.[1]. functions/src/__tests__/onUserDelete.spec.ts shows the whole pattern.

Take a trigger's handler at the top of the file, not inside a test. vi.clearAllMocks() in a beforeEach empties the mock's call list, so a handler read inside a test is missing, and a test that returns early when it is missing passes without checking anything.

Feature switches in specs

Core specs test Arc CMS with its features on, whatever an app turns off in src/custom/features.ts, so an app that turns features off can still run the whole suite:

  • src/test/setup.ts mocks src/custom/features.ts as empty: every feature is on except the installable app (PWA), which is off unless asked for.
  • functions/src/__tests__/setup.ts mocks the functions' list of features with all of them on.

A spec about a particular choice mocks the file itself, and its mock wins:

vi.mock('../../../custom/features', () => ({ CUSTOM_FEATURES: { on: ['pwa'] } }));
const featuresOff = new Set<string>();
vi.mock('../feature-flags.js', () => ({ isFeatureOn: (id: string) => !featuresOff.has(id) }));

The feature ids are listed in Feature ids.

Specs that meet an app's pages

The same suite runs in an app, so a core spec must not assume the app is empty. Where a spec touches something an app can change, it reads the app's answer instead of a fixed one:

  • Where a role lands after sign-in: compare with homeFor(role), not with /user/dashboard, because src/custom/home.ts may send people elsewhere.
  • The route list: a route may group children without a component of its own, and the app's routes in src/custom/routes.ts are left out of the check that gives every URL to a feature or to core.
  • The admin menu: an item that links to one of the app's routes opens the app's page, so the menu check accepts it whatever feature the item names. explicitRouteUrls() and isServedBy() in src/test/route-urls.ts read the app's routes for both checks.
  • A file the check should not find: use a throwaway folder as the repo root, because an app has files such as firestore.app.rules that Arc CMS does not.
  • The website: a spec about Arc CMS's own header, footer, sign-in panel, placeholder home page or templates reads them from public/_site/, never from virtual:arc-site, readSiteFile() or the built siteManifest(), which show the app's site when src/custom/site/ has one. A spec about pages the app may supply (the legal notice's terms and privacy links) passes its own answer, such as legalNoticeUrls(() => false), or sets one with setSiteManifestForTesting().

To check a change against an app's site, put a few files in src/custom/site/ (a header without a search box, a home page, a terms page) and run the suite: only the check that Arc CMS ships its starter files empty may fail, and it is skipped in an app.

Rules tests

The security rules are tested against the Firestore and Storage emulators:

npm run test:rules

It combines the core and app rules, starts the emulators with the Firebase CLI, and runs tests/rules/ with vitest.rules.config.ts. It needs the Firebase CLI and Java. Run it whenever a rules file changed. How to write a rules test is in Security rules.

Docs checks

The docs have tests too. They run with npm run test, and on their own with:

npm run check:docs

They fail on a broken link, a path or npm script that does not exist, a missing feature page, or a writing rule broken. See Writing docs.

Before you finish

A change is done when the whole suite passes, with the rules tests when rules changed, and the docs agree with the code: see Docs and tests are part of done.
