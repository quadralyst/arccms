Automations

An automation says what happens when an event fires: send an email, create an in-app notification, or add the person to a list or take them off one. Admins set them up on the Automations page; your code can add events of its own.

What it is

Arc CMS and your code emit events, such as user.signed_up. Each event can have a mapping: an on/off switch and one or more rules. A rule has a name, an optional condition, and actions. When the event fires, every rule that applies runs its actions.

EventFires whenOffered when
user.signed_upA user record is createdAlways
payment.succeeded, payment.failedA payment goes through or failsPayments is on
waitlist.joinedA signup form sign-up is confirmedSignup forms is on
app_user.created, app_user.deletedA person appears in, or leaves, your app's user collectionAudience is on and an app is connected (App audience)
app_user.changed.<field>A watched field of an app user changes; one event per watched fieldSame as above

Arc CMS also emits user.deleted when a user record is deleted. It carries no email address, so its rules cannot send email or change lists. It, and any event your own code emits, shows on the page only once a mapping for it exists.

ActionDoesNot for
Send an emailQueues a template, as transactional or marketing, to the event's email address
Create a notificationAdds an in-app notification of a chosen type, with a title, body and linkApp user events
Add to lists, remove from listsChanges the person's list membership, creating the contact if neededApp user events; needs Audience

Emails from a rule go through the Email engine: the master switch, the template's active switch and a disabled contact apply to every rule email. A marketing email also needs consent and is blocked by any suppression entry; a transactional one is blocked only by a bounce or a complaint. Rule emails have no switch of their own under Email Features.

Turn it on or off

Automations are always on: they are core, not a switchable feature. Each event has its own switch on the page, and each rule can be turned off on its own. Every event starts switched off, so nothing runs until an admin turns it on. With Email marketing on, the Event mappings tab on Email, Announcements switches events on and off too.

Events of a feature that is off are not offered, and never fire. Their saved mappings stay, for when the feature is on again. Without Audience, list actions are hidden, and a saved list action is recorded as not run.

Set it up

Nothing to set up beyond a working Email engine for rules that send email. The built-in events are listed from the start, switched off. An event's mapping is created by its first save, or, for the built-in events, when the email system's defaults are seeded (opening Email, Announcements does this). The seeded user.signed_up and payment.succeeded mappings come with a Default rule that adds the person to All Users or All Customers.

Use it

  1. Open Admin, Settings, Automations (/admin/settings/automations) and open an event.

  2. Turn on Run this event's rules.

  3. Click Add rule, name it, and choose its actions: tick Send an email and pick a template and its Email type (transactional or marketing); tick Create a notification, pick a type and write the title, message and optional link; or pick lists under Add to lists or Remove from lists.

  4. For a field change (app_user.changed.<field>), set a condition on the old value (was), the new value (becomes), or both: anything, exactly, any of, or none of. Separate several values with commas.

  5. Save. Each event saves on its own, and a change saved meanwhile on another event is kept.

A rule needs a name and at least one action, an email needs a template, and a notification needs a type and a title; the page will not save until they are there.

Conditions compare values as text and ignore case, and treat empty, null and missing as the same empty value. So exactly true matches a stored true, exactly pro matches Pro, and any of: , free matches a free plan written either way.

An email template, and a notification's title and body, can use the event's data as ##KEY## tags, for example ##WAITLIST_ID## in an email on waitlist.joined. Only events with a userId (user.signed_up, the payment events, or your own) can create a notification.

Some templates are filled by another feature with data a rule does not have: signup_otp_email, waitlist_verify_otp_email, notification_generic_email and admin_digest_email. Sent from a rule they would go out with a blank subject and body, or a code nobody asked for. The page does not offer them, and the server refuses them (the result is template_not_for_rules).

Events are extra to what Arc CMS already does. For example, the welcome email and the admin alert on a new sign-up are sent whether or not user.signed_up has rules, so a rule that sends a welcome email sends a second one.

Extend it

Emit your own events from your Cloud Functions in functions/src/custom/. The event is stored and processed by onAppEventCreate; the admin decides what it does:

import { emitAppEvent } from '../email-core/appEvents.js';

await emitAppEvent('order.shipped', {
  userId: uid,                          // the Firebase Auth uid, for notifications
  contactEmail: email,                  // where an email goes
  data: { TRACKING: 'AB123' },          // fills ##TRACKING## in a notification
}, { id: `order-shipped-${orderId}` }); // optional: the same id is processed once

To make the event appear on the Automations page, give it a mapping: add a key for it under mappings in the Settings/event_mappings document, for example "order.shipped": { "enabled": false, "rules": [] }. From then on, admins edit it like any other event.

An event with no userId gets no notification. An event with no email address (neither contactEmail nor a user with an email) sends no email and changes no lists.

What it stores

WhereHolds
Settings/event_mappingsThe mappings, under mappings, keyed by event: enabled and rules. A rule has name, enabled (off only when false), an optional when: { from, to } where each side is { equals }, { anyOf: [...] } or { noneOf: [...] }, and its actions: sendEmail: { templateType, category }, createNotification: { typeKey, titleTemplate, bodyTemplate, link }, addToLists and removeFromLists (list ids). Actions stored on the mapping itself run first, as a rule named default.
AppEventsOne document per event: type, createdAt, processed (false until handled), and when present userId, contactEmail, appUserId and data; once handled, processedAt and results

The function is onAppEventCreate, a Firestore trigger on AppEvents, deployed as arccms-onAppEventCreate. See Data model and Cloud Functions.

Who can do what

WhoCan
AdminRead and write Settings/event_mappings (the Automations page); read AppEvents
Nobody from a browserCreate or change AppEvents. Only Cloud Functions emit events.

Troubleshooting

Every processed event records what happened in results on its AppEvents document. Read it in the Firebase console, or for app user events on the person's Recent activity. status is at the top; each rule's outcome is under its name, for example results['Rule 1'].email.

results saysWhy, and what to do
status: 'no_mapping'The event has no mapping. Add one (see Extend it).
status: 'disabled'The event is switched off on the page.
status: 'no_matching_rule'The event has no rules, every rule is off, or no condition matched the old and new value.
email: 'no_template'No template of that type exists. It was deleted, or its type changed.
email: 'skipped' or 'suppressed'The email engine blocked it; the email log says why (see Email engine).
lists: 'feature_off' or 'not_applicable'Audience is off, or it is an app user event, where list actions do not apply.
status: 'error'Something failed; message says what. The function logs have the details.
