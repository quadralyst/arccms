Sign-in methods

People sign in on one page with an email, a phone number or Google. You choose which of the three are offered; each account can use any of them it has set up.

What it is

The sign-in page is /signup. It asks one question, "Email" (or "Phone number or email" when phone sign-in is on), and shows Continue with Google when Google is on. What happens next depends on what was typed and whether it is registered:

MethodRegisteredNew
EmailPasswordA code by email, then name and password
Phone numberA 6-digit PINA code by SMS, then name and a 6-digit PIN
GoogleOne tapOne tap; name, email and photo come from Google

Whatever the method, a person is one Firebase Auth account plus one users record (see Users and roles). The record is always created by the server, with the site's default role and the arccms_uid claim already in the first ID token.

  • Email uses Firebase's password sign-in. The sign-up code is Arc CMS's own: it proves the address before the account exists. Forgot password sends Firebase's reset email.
  • Phone number is Arc CMS's own sign-in. The number is kept on the users record, never on the Firebase Auth account. After the right PIN or code the server returns a custom token and the browser signs in with it.
  • Google is Firebase's Google provider. Firebase keeps one account per email, so a Google sign-in with the address of an existing account lands on that account.

After signing in, people go back to the page that sent them to sign in (/signup?redirect=/learn), else to their role's home page, which an app sets in src/custom/home.ts (see Set up sign-in).

Turn it on or off

Sign-in is core and always on. Email sign-in is always offered. The other two have switches under Settings, User Settings, Sign-in methods:

SwitchDefaultAlso needs
Enable User SignupsOnNothing. Off: only admins can add people (Users, Add User), and existing accounts still sign in.
Phone numberOffThe sms feature (on by default), SMS settings, and one Google Cloud setting (see Google Cloud setup for phone sign-in). The switch checks that setting before it turns on. With sms off in src/custom/features.ts, the switch is hidden, phone sign-in is off whatever it says, and the phone functions are not built.
GoogleOffThe Google provider turned on in the Firebase console.

The Default Role for New Users is set on the same page. The switches take effect at once, with no deploy.

Set it up

  1. Firebase console, Authentication, Sign-in method: Email/Password must be on (email sign-in uses it). Turn on Google if you want Google sign-in. See Configure a project.

  2. Deploy the functions, Firestore rules and indexes (see Deploy).

  3. Phone numbers only: set up SMS under Settings, SMS: the provider, the default country code and the allowed country codes. Keep the Test provider while trying it. See SMS. The project also needs the Google Cloud setting below; the deploy offers to make it.

  4. Settings, User Settings: leave sign-ups on, and turn on Phone number and Google as wanted.

  5. Try each method on /signup in a private window.

Google Cloud setup for phone sign-in

The last step of every phone sign-in creates a custom token, which the functions sign as their own service account (for 2nd gen functions, <project-number>-compute@developer.gserviceaccount.com). A new Firebase project cannot do that until:

  • the IAM Service Account Credentials API (iamcredentials.googleapis.com) is on, and
  • that service account has the Service Account Token Creator role (roles/iam.serviceAccountTokenCreator), granted on the account itself or on the project.

Three things make sure nobody finds out the hard way:

  1. The deploy. A deploy that includes functions, with the sms feature on, checks both once per project with gcloud and, in a terminal, offers to set up what is missing. Without gcloud it says so once. It never stops the deploy (see Deploy).
  2. The switch. Turning on Phone number under Settings, User Settings first signs a throwaway token (the checkPhoneSignIn function; it creates no account). If that fails, the switch stays off and the page shows what is missing, a gcloud command for this project to copy, a link to the Google Cloud console, and Check again. With phone sign-in already on, the page runs the same check whenever it opens. If the check itself cannot run (the function is not deployed), the switch turns on anyway, with a warning.
  3. A failed sign-in. If the setting goes missing later, the person signing in sees "Sign-in isn't ready on this site yet. Please contact the site's team.", and every admin gets a notification (admin_sign_in_setup) saying what to fix, at most once a day.

To set it up by hand, with your project id and service account:

gcloud services enable iamcredentials.googleapis.com --project=<project-id>
gcloud iam service-accounts add-iam-policy-binding <service-account> --member=serviceAccount:<service-account> --role=roles/iam.serviceAccountTokenCreator --project=<project-id>

Granting a role needs the Owner or Security Admin role on the project. In the console, the role is added under IAM and admin, IAM.

Use it

Email

A new address gets a 6-digit code by email (template signup_otp_email), valid for 10 minutes, with 5 tries and at least 60 seconds between codes; an address gets at most 5 codes an hour. The new account is marked email-verified only when it is created from the browser that entered the code. Passwords need at least 8 characters.

Waking the functions early

Each step of a sign-in is its own Cloud Function, and one that has not run for a while takes a few seconds to start. So that the person does not wait for each one in turn, the sign-in page calls the functions its sign-in methods use with { warmUp: true } as it opens, at most once every 5 minutes (SignInService.warmUp(), the list is SIGN_IN_FUNCTIONS). A warm-up call does nothing and returns at once, before any check or rate limit, so it costs a function call and nothing else. The code email is sent by the function that creates the code, not by the email trigger, which would be one more function to start.

Phone number

  • Numbers can be typed or pasted in any common format; a number without a country code gets the default one. Numbers outside the allowed country codes are refused (by default only 91).
  • SMS codes are 6 digits, valid for 10 minutes, with 5 tries, 60 seconds between codes and at most 5 codes an hour per number.
  • PINs are 6 digits. One digit repeated, a straight run (123456, 987654) or a common pattern (121212) is refused. The 5th wrong PIN in a row locks it.
  • Forgot PIN, a locked PIN, or a number that never had one: an SMS code, then a new PIN. A reset signs out every other session.
  • With the Test SMS provider no SMS is sent: the sign-up page shows the sign-up code. PIN reset codes appear only in SMS Logs, for admins, unless an admin turns on Show PIN reset codes on screen in Settings, SMS (see SMS). Link codes are always in SMS Logs only.

Google

A first-time Google user gets a record straight from their verified Google profile, with no form. If the address already has a password account, the person is asked for the password once and Google is then connected to that account.

Profile, Sign-in methods

On the profile page (/profile, or /user/profile in the member area) a signed-in person can add or change their email or, with phone sign-in on, their phone number (each with a code), change their PIN, and connect Google. A password or PIN is asked for only when the account has none yet.

Moving an email or number to another account

When the email or number someone adds is already on another account, the page says so, and verifying the code moves it. The other account keeps all its data:

  • If it still has a way to sign in, its owner gets an in-app notification that the email or number moved.
  • If it has none left, it is detached: kept, blocked from signing in, listed under Users, Detached accounts, and the admins are alerted.
  • An email that moves is also freed on the old Firebase Auth account, together with its password and Google sign-in, so they cannot reopen the old account.
  • Every move is recorded in account_transfers.
  • A sign-in that belongs to another app sharing the Firebase project is never changed (see Sharing a Firebase project).

Extend it

  • Send people to sign in and back: link to /signup?redirect=/your-page.
  • Where people land by role: src/custom/home.ts, described in Set up sign-in.
  • The sign-up code email is the signup_otp_email template (see Email engine).

A new sign-in method (another provider) is a change to core, not something an app adds.

Who can do what

  • The sign-in functions need no account, since people call them to sign in. Codes, PINs and requests have the limits under Use it.
  • A person cannot create their own users record, and cannot change their own email, phone or phoneVerified; only the server does, after a code. They may only clear emailVerified.
  • signup_otps, phone_otps, phone_index, auth_pins and _rate_limits are closed to every browser.
  • Admins can read account_transfers and SMS Logs, and are the only ones who read or write Settings/sms. Settings/users is public to read and admin only to write.

Troubleshooting

SymptomCause and fix
"This way of signing in is not turned on for this site."The Firebase provider is off. Turn on Email/Password or Google in the Firebase console.
"Phone sign-in is not turned on for this site."Turn on Phone number under Settings, User Settings (it needs the sms feature).
"Google sign-in is not turned on for this site."Turn on Google under Settings, User Settings, as well as in the Firebase console.
"New accounts can't be created on this site right now."Sign-ups are off. Turn them on, or add the person under Users.
"This account doesn't have access to this site."The address has a Firebase sign-in but no Arc CMS record, such as another app's user in a shared project. An admin adds them under Users.
A number is refused as not allowedIts country code is not in the allowed list under Settings, SMS.
No SMS arrivesThe SMS provider is Test, which sends nothing. Look in SMS Logs, or switch the provider (see SMS).
The first sign-in after a quiet spell is slowThe functions were not running and had to start. The page starts them as it opens, so the wait is shortest when the person opens it before typing. A function added to a sign-in step belongs in SIGN_IN_FUNCTIONS in src/app/pages/(auth)/sign-in.service.ts, with if (isWarmUp(request)) return WARM; as the first line of its handler; a test checks both.
"Too many tries. Reset your PIN with a code."The PIN is locked after 5 wrong tries. Use Forgot PIN.
"Sign-in isn't ready on this site yet. Please contact the site's team."The functions cannot sign the sign-in token: the Token Creator role or the IAM Service Account Credentials API is missing. Open Settings, User Settings: it shows the fix for this project. See Google Cloud setup for phone sign-in.
The Phone number switch will not turn onThe same setup is missing, and the page shows how to fix it. After fixing it, click Check again, then turn the switch on.
