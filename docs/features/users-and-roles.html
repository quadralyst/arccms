Users and roles

Admins add, block and delete people and change their role or phone number under Users, never leaving the site without an admin; people edit their own profile and can delete their own account. A role on each record decides what someone may do.

What it is

A person is one Firebase Auth account plus one record in the users collection. The record id is not the Auth uid: the record carries the uid in its uid field, and the account carries the record id in its arccms_uid claim.

The record's role is copied onto the account as the arccms_role claim, which the security rules and functions check. The roles are:

RoleMay
adminEverything, including the whole admin area (/admin/...).
userTheir own record, profile and member area (/user/...), and what your app grants.

How claims are set, refreshed and checked, and how an app adds its own roles, is in Roles and claims. How people sign in is in Sign-in methods.

Turn it on or off

Users and roles are core and always on. They belong to no switchable feature.

Set it up

  1. The first admin comes from the setup wizard on a fresh install: see Create the first admin.

  2. Settings, Sign-up and roles: choose whether people may sign up on their own (Let people sign up, on by default) and the Role for new users (user unless you change it).

The default role applies to every self sign-up. Setting it to Admin makes everyone who signs up an admin.

Use it

Users (admin)

Admin, Users (/admin/users) lists every record with name, email, phone, role and status. An account an app created for someone with no email and no phone shows App account in the email column (see App accounts).

The status column says Active or Blocked, and the role shows by its name. When the list cannot be read it says so in a plain sentence with Retry. A search, Detached accounts or the All, People and App accounts switch that leaves no rows says Nothing matches, with Clear filters to go back to everyone.

  • Add user creates the sign-in account and the record together, with a temporary password you share with the person, typed twice so a typo never sets one nobody knows (the same rule as members' passwords: at least 8 characters and not easy to guess, or at least 6 in an app that chose simple passwords, see Passwords). Sign-ups do not have to be on. If the address already has a sign-in account (another app's user in a shared Firebase project), that account is reused and the record is marked authOwner: 'shared'. When its email is verified it is left unchanged and the person keeps their existing password. When it is not and Arc CMS made it (a password sign-in only, with no other app's claims, in a project Arc CMS has to itself or made in the last few minutes), anyone could have made it by typing the address, so it gets the temporary password you typed (checked by the same rule) and every session on it ends: only the person you tell can sign in. Any other unverified account, such as another app's user, is reused untouched and keeps its own password, so it can only be added with the User role: whoever made it might not be the person you mean. Ask them to verify their email first to give them another role. The message after saving says which happened. A sign-in that already has an Arc CMS record is refused.
  • Role, in Add user and Edit user, is Admin or User. A record with another role keeps it on the list, shown in plain words (propertyOwner reads "Property owner"), and a list opened for one role, such as /admin/users/admin or /admin/users/propertyOwner, starts Add user on that role. Choose Admin to make a second admin. On Edit, a new password is set first, then the role, by the adminSetUserRole callable; a refused role saves nothing more, and the message says whether the password was set. Your own record has no role choice: another admin changes your role. The server refuses to take the role away from the last active admin, and refuses a role above User for a sign-in whose email was never verified unless the admins hold its password: Add user made it, or an admin has set a new password for it in Edit user since. So to make an admin of someone who signed up themselves and never verified their email, ask them to verify it, or set a new password for them in Edit user and tell them it. A phone account has no email to doubt.
  • View opens the record in a side panel, and Edit changes the person's name there. A person who has no email can be saved without one; an email typed in is still checked. Change number, for a member with a phone number whose sign-in is Arc CMS's own, puts in a new number for someone who lost their phone (the adminSetPhone callable). The number must be valid, from an allowed country, and on no other account. Their PIN and remembered devices are cleared and their sessions ended, so the next time they sign in with the new number they get a code at it and choose a new PIN, which marks the number verified. A member with an email is told by the Account security notification. Set a new password sets a new password for someone with an email, typed twice: it must pass the same password rule as every new password (see Passwords), goes to their sign-in account only (never to the record) and ends every session they have. The record keeps when (adminPasswordAt), which lets an unverified email be given a higher role. It is not offered for a sign-in shared with another app (that app changes it) or a locked app account (its app does). People change their own email or phone number on their profile, with a code (see Sign-in methods).
  • Block sets isActive to false, through the adminSetUserBlocked callable. The person's Arc CMS claims are removed and every session is ended within the hour, and they cannot sign in until an admin presses Unblock, which puts the claims back. A detached record has no Unblock: its sign-in moved away, so delete it instead. A demoted admin's sessions end too, so the old role is gone within the hour.
  • Never without an admin. Your own row has no Block and no Delete, and your own record no role choice: another admin does that. The server refuses to block, delete or demote the last active admin (counting only admins who are not blocked and have a sign-in of their own), and refuses an admin whose own record is no longer an active admin's, even while their token still says admin: a blocked or demoted admin cannot undo it. Moving the only email or number off the last admin to another account, and an app deleting the last admin with deleteAppAccount, are refused the same way. The rules refuse every browser write of role, uid, isActive, status, phone, phoneVerified, by, authOwner or adminPasswordAt and every delete of a record, an admin's too, so no page can skip the checks. A refusal shows its reason on the page, in the admin's language: Add user, Edit user and the list map the server's reason (such as last-admin, weak-password, unverified-account or an address that already has a user) to their own words, and never show the server's English. The detail stays in the browser console.
  • Search finds a person by any part of their name, email or phone, in any case; digits find a number however it is written. Firestore cannot search inside a field, so the first character reads the accounts of the list you are on (up to 5,000, and the page says so if there are more), kept current while the search stays open: typing more and turning pages read nothing, and clearing the box closes it.
  • All, People and App accounts, above the list, narrow it to everyone (the default), to the people, or to the accounts an app made (by: 'app'). They work with Detached accounts and with the role pages such as /admin/users/admin.
  • Detached accounts shows records whose only email or phone number moved to another account (see Sign-in methods). They are kept and cannot sign in; an admin can delete them.
  • Delete asks first, saying what goes: the record, the sign-in (unless another app shares it), the PIN, files, profile photo, feedback and notifications, while the audience contact stays. The adminDeleteUser callable then removes the record, and the server removes everything listed below.

Profile (the person)

The profile page is /profile, and /user/profile in the member area. It shows the person's photo and name; an admin's also says Admin, while a member's names no role or status. People change their name and photo, manage their sign-in methods and password, and, unless they are an admin, delete their own account under Delete account. The cards (details, sign-in methods, password) depend on the site's sign-in settings, so they appear together: at once from the copy this browser kept, or after a short loading line the first time, and the page does not jump while it fills. A change of name or password shows Cancel to the left of its save button.

Within 10 minutes of signing in, Delete my account deletes at once, after the person confirms. Later, the page asks for a fresh code, sent to the person's own email address or phone number, and deletes once it is typed: nobody has to sign out and in again (see Ask for a fresh code, purpose delete-account). Only an account with neither an address nor a number to send a code to is asked to sign in again. The code's proof is used up by the attempt, so a delete that fails after it says "We couldn't delete your account. Please try again with a new code." (reason delete-failed), and the next try sends a new code. Admins cannot delete themselves: another admin removes them under Users.

What deleting an account removes

Whoever deletes it, the users record goes first, and then the onUserDeleted function, in this order:

  1. Access: removes the Arc CMS claims and ends every session, before anything else, so a failure later never leaves a removed admin an admin.

  2. Firestore: every subcollection under users/{docId} at any depth, the person's Feedback, and their in-app Notifications.

  3. Storage: the per-user folder users/{docId}/ (under the install's upload folder, if it has one) and the profile photos in avatars/{uid}/.

  4. Sign-in: the Firebase Auth account, unless another app owns or shares it (authOwner is host or shared), plus the email_lookup entry, the phone number index and the PIN, and an app's own PINs and its gates' counts of wrong phone PINs (see PINs for your app).

  5. Event: user.deleted on the event bus, with userId (the Auth uid) and data.userDocId, once every step above has worked.

A step that fails makes the whole cleanup run again (each step is safe to repeat) for up to an hour after the delete.

A sign-in deleted some other way, such as by the person's browser, leaves the record as it is. The onSignInDeleted function then emits user.signInDeleted instead, and nothing is removed. An admin can still delete the record. See Follow the account contract.

The person's contact (their address in the audience): a person deleting their own account also erases it, with its lists, consent and form sign-ups, and an erasure receipt is kept in ErasureLog. An admin deleting a user only unlinks the contact from the account (with the audience feature), since the address may have been on a list before the account existed.

Kept: payment records (Transactions, CreditLedger) are not deleted. Data your app keeps outside users/{docId} is your app's to delete: see Follow the account contract.

Extend it

  • Per-person app data belongs under users/{docId}/... in Firestore and in the per-user Storage folder, so deleting the account removes it with no extra code. See Follow the account contract.
  • Clean up data kept elsewhere with a trigger on users/{docId} deletes in functions/src/custom/, or by reacting to user.deleted (see Automations).
  • Your own roles: Arc CMS never reads or writes a plain role claim, so an app may use it for its own roles. Never name an app claim arccms_*. See Roles and claims.
  • Where each role lands after signing in: src/custom/home.ts.

Cloud Functions:

FunctionDoes
adminCreateUserCallable, admins: Add user.
adminSetPasswordCallable, admins: Edit user, Set a new password.
adminSetUserRole, adminSetUserBlocked, adminDeleteUserCallables, admins: Role on Edit, Block and Unblock, Delete. The caller must be an active admin by their own record (not-active-admin). Each refuses to leave the site without an active admin (last-admin); changing your own role, block or record is refused (own-account); a raised role on an unverified email sign-in whose password the admins do not hold is refused (unverified-account); unblocking a detached record is refused (detached); a locked app account's role and deletion are its app's (app-managed).
adminSetPhoneCallable, admins: Edit, Change number. Refuses a number on another account (number-taken), an invalid one or one from a country the site does not allow, a sign-in another app shares, a locked app account and a record with no sign-in.
deleteMyAccountCallable: the person deletes their own account. Never a locked app account: its app deletes it (App accounts).
refreshMyClaimsCallable: puts the claims back on the caller's token at sign-in.
claimFirstAdminCallable: the setup wizard's first admin, once.
syncAllUserRolesCallable, active admins (by their record): re-applies every account's claims from its record, 200 records at a time; a blocked or detached record gets none.
fillAccountSourcesCallable, admins: gives every record with no by the value unknown, so People finds it. The users page calls it by itself, once, the first time it lists people and finds such records.
onUserRoleChangeOn every record write: applies the default role to a sign-up, and keeps the claims in step with the role and the block.
onUserCreated, onUserCreateWelcomeEmailOn a new record: the email lookup, the admin alert (not for an app account) and user.signed_up event, and the welcome email.
onUserDeletedOn a deleted record: the cleanup above.

See Cloud Functions and Data model.

Who can do what

ActionWho
Read a users recordThe person themselves, and admins
Create a recordThe server only. Every sign-up creates its record there, and so does Add user.
Edit own recordThe person, except role, uid, isActive, status, authOwner, email, phone, phoneVerified, the detach fields and the plan and credit fields
Edit any recordAdmins, except role, uid, isActive, status, phone, phoneVerified, by, authOwner and adminPasswordAt
Change a role, block, unblock, delete a recordAdmins, through the callables above, which keep an active admin. The server itself (the Admin SDK) is not held to the rules. A role written by anyone else is reverted by onUserRoleChange.
Read a per-user Storage folderThe person and admins. The person's own uploads there are allowed by the app, in storage.app.rules.
Write avatars/{uid}/The person: a JPEG, PNG or WebP photo under 1 MB

Troubleshooting

SymptomCause and fix
A new admin still sees "unauthorized"Their token has the old claims. Signing out and in again refreshes it.
Claims look wrong on many accountsEach person's claims are set again from their record the next time they open the site signed in. To re-apply every account at once, call the syncAllUserRoles callable while signed in as an admin; there is no button for it.
People leaves out someone who is in AllTheir record has no by: it was made before Arc CMS recorded how an account was made, and Firestore leaves such a record out. The page fixes this itself with fillAccountSources; if it stays, deploy the functions and choose People again.
People or App accounts shows nothing, and the browser console asks for an indexThe indexes for these filters are in firestore.indexes.json: deploy them (firebase deploy --only firestore:indexes) and wait for them to build. Sorting by another column than Joined needs an index of its own, as it does with Detached accounts.
"For your security, sign in again, then delete your account."The last sign-in is more than 10 minutes old and the account has no email address or phone number to send a fresh code to. Press Sign in again, then delete.
An admin has no Delete account sectionAdmins cannot delete themselves. Another admin deletes them under Users.
Deleted a user, but their sign-in still existsThe record was marked host or shared: the sign-in belongs to another app and is kept, without Arc CMS claims.
Add user says "A user with this email already exists."A record already has that address. Edit that record instead.
"This is the only active admin. Make someone else an admin first."Blocking, deleting or demoting this admin would leave the site with none. Give another person the Admin role on Edit first.
"This person's email was never verified..." when choosing AdminThey signed up themselves and never proved the address. Ask them to verify it, or set a new password for them in Edit user (tick Set a new password and choose Admin in the same save), then tell them the password.
"Your admin access has ended. Sign in again."Your own record was blocked or demoted by another admin. Your token still said admin for a while, but the server reads your record.
An app's page that wrote role, isActive or status, or deleted a user, now gets "Missing or insufficient permissions"The rules refuse those writes from every browser. Call adminSetUserRole, adminSetUserBlocked or adminDeleteUser instead.
